# DC-29 — the packed smoke's banner check was stale AND non-contiguous

Status: FIXED in the 0.18.0 ceremony (2026-08-30).
Class: release-gate false negative. No product defect.
Surface: `bench/packed-pty-smoke.sh`.

## The defect

Run bare at the 0.18.0 ceremony, the packed smoke reported

```
FAIL banner: expected v0.4.0
```

Two independent faults, either of which alone produces a
release-blocking FAIL on a perfectly good artifact:

1. **The default was a frozen literal.** `VERSION=${EXPECTED_BANNER:-v0.4.0}`
   named the version of the round that wrote it. Every ceremony since
   has had to pass `EXPECTED_BANNER` or read a FAIL; nothing said so.
2. **The needle was never contiguous.** The banner renders
   `kiso <version>` — no `v` — and the compositor emits it as
   `<bold>kiso<reset><dim> 0.18.0<reset>`, so an SGR reset sits between
   the name and the number. `grep -q "kiso 0.18.0"` on the raw capture
   cannot match, and neither can `v0.18.0`.

Fault 2 is the third time this class has been hit in three days. DC-25
recorded it from the 0.17.0 dogfood scan (waiting on `✦ took `, which
straddles an SGR reset). It was hit again inside the R4 round, on a test
assertion (`ctrl+r expands`). And then here, in a release script.

The class, stated once: **a needle taken from what the screen LOOKS like
will not match the bytes.** Strip SGR first, or match a span that no
style boundary crosses.

## The fix

- the default is the workspace's own version, read from the root
  `package.json` at run time — it cannot go stale;
- the grep runs on an SGR-stripped copy of the capture.

Verified: `bash bench/packed-pty-smoke.sh` with no environment passes
all four legs at 0.18.0.

## Why this is worth a number

It cost two false FAILs mid-ceremony and, worse, it is the shape of
gate that trains people to pass an override without reading it. A gate
whose default is wrong is not a gate; it is a habit.
