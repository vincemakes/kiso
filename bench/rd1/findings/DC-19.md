# DC-19 — a committed row that reaches neither the screen nor the scrollback

- **id:** DC-19
- **class:** renderer geometry / silent content loss
- **severity:** P1 — a tool call's row disappears with no trace and no
  way to get it back
- **agent:** kiso, every version that has the REL-0152-R1 diff renderer
  (0.16.6 and earlier — NOT introduced by the R3 rounds)
- **found by:** feeding twenty tool calls into a 12-row screen and
  counting the rows that came out
- **status:** OPEN — reproduced, measured, root-caused; the fix is
  proposed below and NOT applied, because both halves of it move the
  window/scrollback contract that a dozen gates pin

## The reproduction

Twenty `run_shell` calls, one of them failing (the failure blocks the
turn fold, which is what forces the twenty rows to commit individually),
fed to a `Body` at H=12, W=80, then one frame:

```
missing: [12]
```

Nineteen rows out of twenty. `cmd12`'s row is in no frame, in no
scrollback write, in no later frame. It was rendered — the instrument
below shows the cell taking the normal render branch — and then it was
dropped between the model and every surface.

No explore tool is involved, so no rollup and no segment machinery is
in the path: this is the draw itself.

## The mechanism

Two independent formulas decide where the window starts and how far the
scroll has gone, and they do not agree:

```
skip  = max(0, all.length + CHROME_ROWS + inputExtra + queue + menu - H)   // the window's top
floor = max(0, committedLines + CHROME_ROWS - H)                           // how far to scroll
```

Instrumented on the failing frame:

```
all=22  frozen=0  committedThisFrame=21  live=1
skip=14  committedLines=21  floor=13  scrolledOff=13
```

The window paints `all.slice(14)`. The scroll pushed `all[0..13)` into
the terminal's scrollback. `all[13]` — the thirteenth call's row — is
above the window and below the scroll: **painted by nobody, scrolled by
nobody.** No later frame recovers it, because `#scrolledOff` has already
passed it and the frame's `all` has moved on.

`skip - floor = live + inputExtra + queue + menu`, so the gap opens
whenever a frame force-commits with a live band still standing. It is
not a rare race; it is arithmetic.

## The invariant it breaks

The screen and the scrollback PARTITION the model: no row in both, no
row in neither. The A7 gates hold the first half ("one answer copy in
the terminal at every frame"). Nothing held the second.

## The fix, and why it is not applied here

Both halves were written and measured:

1. `floor = min(skip, committedLines)` — scroll off exactly the
   committed rows above the window. Closes the loss (`missing: []`),
   and the A7 seam gate goes red: a shrinking live band pulls the
   window's top back over rows already in the scrollback and paints a
   second copy.
2. ...so the window must never reach above what has been scrolled:
   `march = all.slice(max(skip, scrolledOff))`. Closes the duplication,
   and two OTHER gates go red — the A8 blank-band gate ("the W11
   boundary's blank never grows into a pileup band") and the V6-1
   resize/frozen march bound.

Both halves are needed and both are correct in isolation; together they
demand a third decision — what the window shows when the live band
shrinks below what has already scrolled away (today it reaches back;
under the fix it would leave the band short). That is a contract
question, not a patch, and the gates that went red are the contract's
own gates rather than incidental ones.

## Recommendation

Its own round, with the third decision stated in the round spec before
any code moves. The two halves above are the starting point and the
three red gates are the acceptance surface.
