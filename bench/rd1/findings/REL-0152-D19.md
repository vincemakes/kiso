# REL-0152-D19 — kiso inherited whatever terminal it was handed

- **id:** REL-0152-D19
- **class:** renderer / inherited terminal state
- **severity:** P1 — corruption that outlives the process and accumulates
- **agent:** kiso 0.15.9 and every version before it
- **status:** FIXED as a defect in its own right. Its bracket
  hypothesis is **REFUTED** — see [[REL-0152-D1]]: the brackets are
  Terminal.app's Marks, drawn decoration that is not text at all.

## The defect, independent of any symptom

The dock reset the terminal on the way OUT — `ESC[r` for the scroll
region, autowrap on, the mouse off — and reset **nothing** on the way IN.
Every session began in whatever state the previous occupant left.

For this product that is not an edge case. kiso's claim is that it
survives `kill -9`, so *"the last instance died without running its
teardown"* is a supported, expected, advertised way to arrive here. And
REL-0152-D14 made it worse without noticing: a frame turns autowrap OFF
and the cursor invisible and restores both at its end, so a process that
dies BETWEEN those two points hands the shell — and the next kiso — a
terminal with wrapping off and no cursor. `kill -9` cannot be caught, so
entry is the only place that can be repaired.

## The fix

The first frame opens by releasing what it inherited:

```
ESC[r      the scroll region back to the whole screen
ESC[?69l   left/right margin mode OFF (DECLRMM) — ESC[r does NOT
           release margins, which is why resetting the region on exit
           was never enough
ESC[?7h    autowrap back to its default
ESC[?25h   the cursor visible again
```

Sixteen bytes, once per session, idempotent, and correct whether or not
anything was actually left set. It rides the first frame rather than
being a write of its own: a separate write is one more event between the
dock coming up and its first paint, and the PTY gates that wait on the
boot stream feel it.

## What this does and does not claim

It was a hypothesis for the owner's stray `[` and `]`, and it is
**REFUTED**: the owner copied the affected rows and the brackets did not
come with them, so they were never characters. See [[REL-0152-D1]]. The
reasoning below is kept because its first step is still true and is what
should have pointed at "not text" rather than at "confined writes":

- kiso's own bytes cannot produce them. Every chrome row is measured at
  exactly W and written from column 1, so `ESC[0K` plus a W-wide write
  covers the row end to end. Content can survive at column 1 or column W
  only if kiso's writes are **confined to a sub-region** — which is what
  a scroll region or a left/right margin does.
- the owner's own sequence is state that outlives the process: a ctrl+C
  exit brings the brackets on, a relaunch makes TWO, and a resize clears
  them.
- the competitor is immune in the same terminal, and it runs on the
  alternate screen, where inherited primary-screen state cannot reach it.

It is **not demonstrated**. No terminal emulator available here
implements DECSLRM, so the before/after cannot be shown locally. The
cheapest confirmation is the owner installing it; the decisive one is a
`KISO_TRACE_BYTES` capture, which since REL-0152-D17 records stderr too.

## A test assumption this exposed

`settledTerm` in the PTY helpers used `raw.indexOf("\x1b[r")` as "where
the session ended", because that byte was only ever emitted at teardown
— so the first was the last. With a second one at boot it cut there and
replayed almost nothing, and five gates went red on a screen that was
simply never fed. It reads `lastIndexOf` now.

Worth recording rather than quietly fixing: the helper encoded "kiso
emits this exactly once, at the end" as an invariant nobody had written
down, and it was true for years.
