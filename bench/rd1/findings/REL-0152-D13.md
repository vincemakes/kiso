# REL-0152-D13 — a submitted paste writes its whole self to the terminal

- **id:** REL-0152-D13
- **class:** performance / rendering volume
- **severity:** P2 — the remaining half of the "paste is slow" report
- **agent:** kiso 0.15.5 (after D9 made the editor linear)
- **found by:** measurement while chasing the owner's follow-up
- **status:** FIXED

## The measurement

D9 fixed the editor: a paste is now linear, and 146KB costs 6ms with the
compositor wired. The owner still reports slowness, and the next
bottleneck is not compute, it is VOLUME.

Submitting a pasted text as a user turn:

| lines | kiso's time | bytes written to the terminal |
|---|---|---|
| 200 | 4.6 ms | 17,638 |
| 1000 | 3.4 ms | 86,398 |
| 3000 | 10.0 ms | **260,298** |

One frame, a quarter of a megabyte. kiso is done in ten milliseconds and
then the terminal has a quarter megabyte to lay out — and REL-0150-D3
already established this terminal's renderer is the weak link (typed
input lagged seconds behind during heavy streaming, while the local echo
path measured 148ms).

## The shape of the fix

The D8 capsule is already the right idea; it just stops at the composer.
A paste is a capsule while you are editing it and then expands to its
full self in the transcript, which is the one place it helps least: it
is text the user already has, and showing all of it scrolls away
everything they wanted to look at.

The transcript chip should stay collapsed — `[Pasted text +3000 lines]`
with ctrl+r to expand, which is machinery the cells already have — while
the MODEL still receives the whole text. That is exactly the D8
contract, applied one layer further out: the capsule is a display form
everywhere, and content is what gets sent.

## The fix, and what it cost

The chip is bounded at twelve rows — enough to recognise what you sent,
short enough that sending it does not scroll away what you were looking
at — and the bound is on ROWS after folding, so one enormous line is
caught by the same rule as three thousand short ones. The folding stops
at the bound rather than folding three thousand lines to show twelve.

| lines | before | after |
|---|---|---|
| 200 | 17,638 bytes | 1,962 |
| 1000 | 86,398 bytes | 1,962 |
| 3000 | **260,298 bytes**, 10.0 ms | **1,963 bytes**, 0.3 ms |

The notice is outside the chip's reverse video, in the cut-row
vocabulary the rest of the product uses:

```
 pasted line 0
 …
 pasted line 11
└ +388 more lines · sent in full
```

`sent in full` is the whole point of the row. What the MODEL receives is
untouched — the capsule is a display form here exactly as it is in the
composer — and a bounded display of a complete message is not a
truncated message. If the row did not say so it would read as data loss,
which is a worse failure than the one being fixed.

ctrl+r expansion was considered and left out: `expandNext` knows `tool`
and `checklist` cells, and teaching it a third kind is a change to the
cell contract rather than to a renderer. The notice tells the truth
without it.
