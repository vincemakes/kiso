# DC-52 — the inode guard ran a full-root `find` per multi-link file, synchronously, with its stderr on the terminal

- **id:** DC-52
- **class:** P1 — the product freezes and writes over its own screen
- **severity:** **P1.** The event loop stops for the duration of each
  scan, so nothing responds — not `esc`, not `ctrl+c`'s handler, not the
  frame. The child's stderr goes straight to the terminal, past the
  compositor, over the composer. On the owner's machine one call had not
  finished after **eight minutes**.
- **agent:** every version that has had the inode guard. Found
  2026-09-05 in the owner's own session.
- **status:** FIXED in 0.24.4, red before green.

## The measurement

The owner started kiso with the workspace at `~`. The model issued three
parallel `search_text` calls — `Desktop`, `Documents`, `Downloads`.
Documents and Downloads settled in about half a second. Desktop never
did.

From the process table, eight minutes in, under kiso's own pid, on the
same tty, in the foreground process group:

```
find /Users/vinve -xdev -inum 2899861 -print0
```

The terminal was filling with `find: …: Operation not permitted`. The
session log (`~/.kiso/sessions/2026-09-05T00-47-41-09f4.jsonl`) contains
no shell call at all — nothing the model did could have produced that
process. An earlier `search_text` with no `path` had already failed
after twelve seconds with `EPERM scandir ~/Library/Accounts`.

## The mechanism — three faults in one call

`scanFile` called `inodeReadPolicy` for EVERY file; a file with
`nlink > 1` triggered `execFileSync("find", [root, "-xdev", "-inum", …])`.

1. **`execFileSync` without `stdio` gives the child the parent's
   stderr.** That is the terminal. The compositor owns the screen and
   paints by absolute addressing; a foreign writer to the same fd lands
   between its rows. This is why the composer was overwritten.
2. **The scan is unbounded, and SYNCHRONOUS.** With the root at `~` a
   single scan is tens of seconds, and it runs once per multi-link file.
   Because it is synchronous the event loop is frozen throughout — which
   is the honest explanation of "the `thinking…` row sat there and `esc`
   did nothing". The product was not waiting. It was stopped.
3. **A directory the OS refuses failed the whole tool.** An unreadable
   FILE has always been skipped (`scanFile`'s catch); an unreadable
   DIRECTORY threw out of `walk` into the outer handler. On macOS that
   is routine, not an edge case: `~/Library/Accounts` and its neighbours
   are TCC protected, so any search under `~` died on one of them.

## The fix

- **`search_text` does not run the guard at all.** A search returns a
  160-character excerpt of a line; a disk traversal to decide whether it
  may is not a trade anyone would make. A multi-link file is skipped and
  COUNTED, and the count is said — `… N multi-link files skipped
  (read_file verifies them individually)`. Fail-closed is unchanged at
  zero cost: the external-link case the guard exists for is still
  refused, and the legal case is refused too, which is a loss of
  coverage rather than of safety.
- **`read_file` keeps the guard, bounded and asynchronous.** `execFile`
  with a 2s budget; a scan that outruns it is fail-closed exactly as an
  unverifiable one always was — refused, never hung. The async form
  pipes the child's streams into the callback, so there is nowhere for
  its stderr to go. The verdict is cached per `(dev, ino)`.
- **`walk` skips EACCES/EPERM directories and counts them**, into the
  same note. Same fact as an unreadable file, same remedy.

## The gate

A fixture with both shapes — a hard-linked file and a directory at
`0o000`. `search_text` completes in bounded time, its result carries
both counts, and **nothing reaches the process's own stderr**.
`read_file` still refuses the hard-linked file, promptly.

## Belongs with

DC-49, whose OPEN question is what a workspace rooted at `~` costs —
this is part of that cost and should be read with it. Round 4/5's
adversarial hardening, whose boundary is kept and whose price is not.
