# REL-0152-D8 — a long paste pasted the whole thing into the composer

- **id:** REL-0152-D8
- **class:** interaction / composer
- **severity:** P2 — a routine gesture destroys the screen
- **agent:** kiso 0.15.3
- **found by:** owner dogfood, 2026-08-25
- **status:** FIXED in the 0.15.4 editing batch

## The behaviour

Pasting a long text into the composer inserted every character of it.
The composer grows a row per line, so a 40-line paste took the input area
to the top of the terminal, pushing the panel, the status row and the
conversation off screen. The owner's report named the expected shape
directly: it should abbreviate, the way the reference implementation
does.

## The fix

The buffer holds a capsule — `[Pasted text #1 +40 lines]` — and the text
lives beside it in a map. The line that LEAVES the editor is expanded
back to the text.

That ordering is the design. The capsule is a display form and can never
truncate what is sent, because expansion happens on the way out and reads
from a map the display cannot edit. Deleting the capsule deletes the
paste, which is how a paste is taken back.

The threshold is 8 lines or 900 characters — lines first, because lines
are what break the layout; the character bound catches the pathological
one-liner that wraps to the same screenful. Below both, the paste is left
exactly as it arrived: a four-line snippet is something you want to see.

## Evidence

- `packages/tui/tests/paste-capsule.test.ts` — 8 cases, red before green:
  the capsule's text, the expansion on exit, prose around it, two
  numbered capsules, deletion, the short-paste no-op, the enormous single
  line, and typed newlines (ctrl+J) staying untouched.
- Real PTY, 40-line paste on the built CLI: the composer shows
  `▌ [Pasted text #1 +40 lines]` and no pasted line appears anywhere in
  the capture.
