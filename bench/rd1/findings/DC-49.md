# DC-49 — kiso's own home is workspace content when the workspace contains it

- **id:** DC-49
- **class:** privacy / workspace boundary
- **severity:** P2 as an information-exposure question, not a
  correctness one. Nothing is corrupted and nothing leaves the machine
  that was not already on it — but the model reads, and can then say
  aloud, everything the human has ever typed into kiso and every
  transcript kiso has ever written.
- **agent:** every version. Found 2026-09-04 in the owner's own dogfood
  of 0.24.0.
- **status:** OPEN — measurement settled, disposition is an owner
  ruling. No product code moved.

## The measurement

The owner started kiso in `~`. Unprompted, within one turn, the model:

1. `list_dir .kiso`
2. `read_file .kiso/history` — the composer's ENTIRE input history
3. said, in its answer, that the history showed the owner had asked
   about the kiso project several times

`~/.kiso/sessions/` holds the full transcript of every session besides.

## Why it happens

The tools' workspace boundary is a PATH test: a read is refused when it
resolves outside the cwd. `KISO_HOME` defaults to `~/.kiso`, so when the
workspace IS `~` — or any ancestor of it — kiso's own state sits inside
the boundary and is, to every tool, ordinary project content.

Nothing is bypassed and no rule is broken. The boundary answers "is this
inside the workspace"; it was never asked "is this KISO'S".

## What is exposed, precisely

| path | content |
|---|---|
| `history` | every line ever typed into the composer, across all projects |
| `sessions/*.jsonl` | full transcripts: prompts, model output, tool results |
| `config.json` | model, mode, theme — the ordinary settings |
| `update-check.json` | the cached dist-tag |

The first two are the ones that matter. They are a record of the human's
work in OTHER projects, reachable from this one.

## The two candidates, for the owner

**(a) kiso's home is not workspace content.** `list_dir` hides
`KISO_HOME` when it would appear at the workspace root; `read_file` and
`search_text` refuse `sessions/` and `history` with a named reason.
`config.json` stays readable — a model helping with kiso's own settings
is a real case and the file holds nothing private. Costs: one more
special case in the tools' boundary, and a model that genuinely wants a
past transcript has to be handed it.

**(b) Nothing changes; the README says so.** Running kiso with its own
home inside the workspace makes kiso's state readable, and a human who
starts in `~` should know that. Costs: it stays true, and it is
discovered by being surprised.

There is a third position worth naming so it is not mistaken for (a):
moving `KISO_HOME` out of `~` by default is NOT a fix — it relocates the
overlap rather than removing it, and any workspace can still contain it.

Not decided here, and not built.

## Belongs with

The tools' workspace boundary (tools-node), ADR-0050's home layout, and
the 0.24.0 dogfood that found it.
