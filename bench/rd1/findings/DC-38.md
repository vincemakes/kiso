# DC-38 — an approval prints its key hint twice on one screen

STATUS: FIXED — found by the UI-1 walkthrough, item 4, against the
installed 0.20.3. Renderer-only; no kernel, no protocol. Remedy (1)
taken; one commit, revertible on its own.

## What was seen

The approval panel, driven for real (mode `default`, the model asked to
append a line to `notes.txt`), at W=100:

```
────────────────────────────────────────────────────────────────────
  edit needs approval — asked by mode:default · /mode accept-edits auto-approves edits
  notes.txt

│   alpha doubles, beta increments, gamma squares, delta subtracts three.
│ + checked
│
 → 1 Yes, run it
   2 Yes, and don't ask again for edit
   3 Show me safer ways to do this
   4 No — let me tell it what to do instead
  ↑↓ move · ⏎ or click confirms · 1-4 instant · esc     ← the panel's row
────────────────────────────────────────────────────────────────────
────────────────────────────────────────────────────────────────────

────────────────────────────────────────────────────────────────────
⏸ run paused              ↑↓ move · ⏎ or click confirms · 1-4 instant · esc
────────────────────────────────────────────────────────────────────
```

The same 48-cell sentence, twice, six rows apart, on one screen.

## Why it happens

One function, two consumers that were written years of rounds apart and
neither of which knows the other renders it:

- `packages/tui-cells/src/approval-panel.ts:670` — `panelBlockRows`
  pushes `panelAffordance(...)` as the block's last row. That is the
  TUI2-R1.5 panel shape: "the affordance — the phase's key hint, ONE
  row" (the file's own header comment, item 3).
- `packages/tui/src/compositor.ts:2006` — `#statusSource` returns
  `{ status: panelStatusOf(panel), hint: panelAffordanceOf(panel) }`.
  That is W21: "while a panel is up, the panel's phase status +
  affordance REPLACE the CLI's painting status".

`panelAffordance`'s own docstring calls it "The status row's
right-aligned hint — the v4 frame's line, verbatim", which says which
of the two sites it was written for.

## The part that makes it worse than a duplicate

It is width-dependent, so it is not reliably visible as a duplicate.
The status row drops its right hint when the left text plus the hint
does not fit. On the ask panel the left text is long
(`⏸ a question for you · answers are durable facts`, 46 cells) and at
W=100 the hint is dropped — one copy. On an approval the left text is
`⏸ run paused` (12 cells) and the hint fits — two copies. So the same
build shows one or two copies depending on the panel flavour and the
terminal width, which is exactly the shape of bug a fixed-width gate
does not catch.

## Why it is a defect and not a redundancy

Law 1.3 — a symbol earns its cell. The second copy carries no fact the
first does not, and it costs the widest row on the screen. The panel's
own row is the one a reader's eye is already inside; the status row's
copy is the one that can vanish. Two copies also means the row that is
supposed to be authoritative is ambiguous.

## Not a defect (checked, so the record says so)

- `or click` is **truthful**. Mouse reporting is off at boot
  (`\x1b[?1000l\x1b[?1006l` at byte 0) and turned ON when the panel
  opens (`\x1b[?1000h\x1b[?1006h`, byte 6103 of the item-4 capture).
  The advertised gesture works.
- The digit range is right: `1-4` with four options.

## Remedy — (1), taken

`#statusSource` returns `hint: undefined` while a panel is up. W21's
other half stands: the panel's STATUS still replaces the CLI's painting
status; only the hint moves out. Each flavour's block carries its own
affordance row already — `approval-panel.ts:670` for the approval,
`pickBlockRows` for the pick, `ask-panel.ts:373` for the ask — so
nothing is lost on any surface, and the ask's row is the width-FITTED
form (`askAffordanceFit`) where the status row's was the full one.

Gate: `packages/tui/tests/dc38-panel-affordance-once.test.ts`, five
cases. It asserts on the SCREEN, not the byte stream: every frame
repaints every row, so counting occurrences in the writes counts frames.
Three widths (100/120/160), because at W=80 the status row has no room
for the hint and the defect is invisible — the reason every fixed-width
gate was blind to it.

red: `expected 2 to be 1` at all three widths
green: 5/5, and `npm run check` EXIT=0

## The other two ways, and why not

2. **Drop the panel block's row instead.** Cheaper to argue from the
   docstring ("the status row's hint"), but it puts the keys the
   furthest possible distance from the list they act on, and it keeps
   the copy that disappears at narrow widths.
3. **Differentiate them** — status row short (`1-4 · esc`), panel row
   full. Buys nothing the panel's own row does not already say, and
   costs a second string to keep in step with the first.
