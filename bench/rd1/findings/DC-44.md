# DC-44 — on Linux the fd-close exit is a SIGHUP death, so the lock is left behind

- **id:** DC-44
- **class:** platform difference in the graceful-exit contract
- **severity:** P3 — nothing is lost and nothing is corrupted. The lock
  file is left where the next launch repairs it, which is the `kill -9`
  contract kiso already keeps. What it costs is one exit path that
  looked graceful on one platform and is not on another, plus 59 bytes
  of dead-pid residue until the next start.
- **agent:** every kiso version on Linux. Found 2026-09-03, when CI ran
  the PTY pool for the first time (the lockfile fix in 0.23.0 is what
  let it get that far).
- **status:** OPEN — the measurement is settled, the disposition is an
  owner ruling. No product code moved; the test leg is marked
  darwin-only with this finding named.

## The measurement

`graceful-exit-release.test.ts` case ③ closes the pty master while the
CLI sits at the prompt, and asserts that the stream EOF fires the EOT
callback so the session lock is released.

That premise holds on macOS. On Linux, closing the master **hangs up the
terminal**, and the kernel sends `SIGHUP` to the session leader. In a
Linux container, 2026-09-03:

- with no handler installed, node dies of signal 1 **before stdin emits
  anything at all** — no `end`, no `close`, no EOT;
- install a `SIGHUP` handler and stdin's `end` does arrive.

So the event the case is named for exists on Linux only if something
holds the signal off first.

## Why kiso does not hold it off

PH-F6 settles that `SIGTERM` and `SIGHUP` keep their **default lethal
disposition**. The reasoning there is about the terminal: a handler that
runs during a hangup can be caught mid-`tcsetattr` and leave the
terminal in raw mode with no process left to restore it — worse than a
lock file nobody released.

So on Linux this exit path is a signal death, the release never runs,
and the lock is left exactly as a `kill -9` would leave it. kiso already
has a contract for that: the next launch identifies the dead holder and
takes over (ADR-0050's rename-away → verify → link). Nothing is lost;
the residue is 59 bytes and one launch long.

## The open item, for the owner

**Should the product install a `SIGHUP` handler that releases the lock
and then re-raises the default disposition?**

The argument for: the lock is a FILE WRITE. It is not in PH-F6's
`tcsetattr` hazard — the danger that ruling names is terminal state, and
releasing a lock touches none of it. A handler that unlinks the lock and
immediately `signal(SIGHUP, SIG_DFL); raise(SIGHUP)` would keep the
death and lose the residue.

The argument against: PH-F6 chose a simple rule — those two signals are
lethal, full stop — and a rule with one exception is a rule that will
grow more. The residue costs nothing that the next launch does not
already repair.

Not decided here, and not built. Recorded so the ruling is made once,
with the measurement in front of it.

## What this finding is NOT

It is **not** "the CLI does not exit on Linux". That was the first
reading of the CI failure and it was wrong. Twenty-five PTY scenarios
reported *"the CLI never exited"* while every one of them had exited
cleanly a fraction of a second earlier — the driver was mis-reading
Linux's EIO. That is a separate defect, in the test apparatus, fixed in
the same round; see the commit that carries this file.

The tell was in the numbers and went unread for a while: every failing
scenario's elapsed time was its NORMAL duration, and every feed had
fired. A CLI that hangs does not finish its work first. **When a driver
says "never exited" and the elapsed time is under a second, read the
driver before reading the product.**

## Belongs with

PH-F6 (SIGTERM/SIGHUP keep their default disposition), ADR-0050 (the
dead-holder takeover the residue relies on), and the 0.23.0 round, whose
lockfile fix is the reason anyone could see this.
