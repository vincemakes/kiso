# REL-0152-D6 — the session picker cannot tell one conversation from another

- **id:** REL-0152-D6
- **class:** session identity / UX
- **severity:** P2
- **agent:** kiso 0.15.3
- **found by:** owner dogfood, 2026-08-25
- **status:** OPEN

## The behaviour

The picker identifies sessions by timestamp plus the FIRST user input:

```
✓ 2026-08-25T07-29-29-32d9   37m · 3 turns · completed clean
✓ 2026-08-25T05-15-24-4166   2h  · 2 turns · completed clean
✓ 2026-08-23T14-23           1d  · 6 turns · completed clean
```

and in the startup list, the first input is shown — which for three of
the owner's five sessions is the word "hello". The distinguishing
information is a timestamp the user has to decode, and a greeting that is
identical across sessions.

The 0.15.2 id fix (RD1B-F9) made ids unique. **It did not make them
meaningful**, and this finding is about the second thing: an id can be
perfectly unique and still tell a human nothing.

## What the reference does

Claude Code does not rely on the first message. It carries a **generated
summary** of the conversation (`src/commands.ts:656`, "Summarize
conversation"), so the list names what the session was ABOUT.

## Shape of the fix

The roadmap's SX-1 already owns "a real session metadata contract", and
this is its first slice. Candidates, cheapest first:

1. **First non-greeting user turn**, not the first turn — free, no model
   call, and would already have separated the owner's three "hello"
   sessions by their actual requests.
2. **A durable human name** the user can set (`/name`), stored in session
   metadata rather than derived.
3. **A generated summary**, refreshed at settle — the reference's
   approach, and the only one that describes a long session accurately.
   It costs a model call, so it needs a policy about when.

(1) and (2) need no model and should not wait for (3).
