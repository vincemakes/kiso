# REL-0152-D14 — the frame never turned autowrap off, and 97 of its rows fill the screen exactly

- **id:** REL-0152-D14
- **class:** renderer / terminal compatibility
- **severity:** P1 — the frame's layout depended on undefined behaviour
- **agent:** kiso 0.15.5 and every version before it
- **found by:** the owner's own byte capture (REL-0152-D12), 2026-08-25
- **status:** FIXED

## What the capture showed

The instrument was built to settle whether the stray `[` came from kiso
or from the terminal. It settled that, and then it found something else.

The capture: Terminal.app 470.2, `LANG=zh_CN.UTF-8`, 80x24, one greeting
turn on the real model. Of the bytes kiso wrote:

- **0** unexplained edge brackets — the only ones are the legitimate
  `[4 extensions: …]` banner;
- **0** bare ESC, **0** writes ending mid-escape;
- and replaying those exact bytes through a correct terminal model
  produces a clean screen, wrap and all.

So kiso's bytes are clean and the characters are made on the terminal
side. The next two numbers say why that is possible:

- **97 rows exactly 80 cells wide** — the box top and bottom, the
  composer row, every gap row the chrome pads out;
- **65 relative cursor-ups** in the same frame.

## The mechanism

A character printed into the last column does not advance the cursor
past it. It sets the terminal's PENDING WRAP flag, and the NEXT printed
character goes to column 1 of the row below. What a terminal does with
that flag when a cursor MOVE arrives instead of a character is not
agreed on: some clear it, some keep it, and the DEC original and the
xterm lineage differ.

kiso filled the last column 97 times and then made 65 relative moves
through exactly that state — on every frame, at any width where a row
happens to fill the screen. The layout was resting on a behaviour
terminals disagree about, which is precisely the shape of a defect that
is invisible on the developer's terminal and constant on the user's, and
that comes and goes with painting rather than with content.

## The fix

The frame opens with `\x1b[?7l` and closes with `\x1b[?7h`: wrapping off
for its duration, on again for everything outside it. With wrapping off,
a character in the last column simply stays there — no flag, no
disagreement, and a relative move means what it says.

Turning it off is safe HERE for a reason that predates this finding:
`#checked` already refuses to emit a row wider than the screen, so there
is nothing for the terminal to wrap and nothing can be lost by not
wrapping it. Prose written OUTSIDE a frame (bodyLog, an error) still
wraps normally, and the dock's teardown restores the mode alongside the
mouse — the terminal outlives kiso, and a mode kiso turned off inside a
frame must never be what the shell inherits.

## What it does NOT claim

This is not proof that D1's brackets came from here. It is a real defect
with a real mechanism, found in the capture taken to investigate D1, and
it is the best available explanation for a layout that is correct on one
terminal and damaged on another. Whether the brackets go with it is
something only the owner's next session can say.

## Also visible in the capture, and not yet resolved

kiso's width table treats the East Asian AMBIGUOUS characters as one
cell — `·` (U+00B7), `…` (U+2026), `—` (U+2014), `✓` (U+2713), `✗`
(U+2717) among them — and kiso uses several of them in its own chrome:
the separator in the status and recap rows, the thinking row's prefix,
the session picker's badges. Under `LANG=zh_CN.UTF-8` a terminal may
render exactly those as two cells. If it does, those rows are wider on
screen than kiso believes and the arithmetic behind `#checked` is wrong
for that terminal. Filed here rather than fixed: the fix is a width-table
decision with its own compatibility surface, and D14 removes the
mechanism that made a miscount destructive.
