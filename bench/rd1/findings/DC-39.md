# DC-39 — a height grow destroys as many rows of history as it adds

- **id:** DC-39
- **class:** renderer geometry / silent content loss (the DC-19 family)
- **severity:** P1 — rows of the transcript vanish from the terminal
  with no trace, on a gesture every user makes
- **agent:** kiso 0.20.3 (the installed binary), and every version with
  the resize adopt that never decreases `#scrolledOff`
- **found by:** the R10 assessment (2026-09-02): the real compositor's
  bytes replayed through a terminal emulator predicted it; the installed
  binary in Apple Terminal, driven by AppleScript and judged by the
  terminal's own buffer, confirmed it twice
- **status:** OPEN — resolved by design under R11 route B (the resize
  reprints the session after erasing the terminal), not patched here

## The reproduction

Apple Terminal, 60×24. A faux model whose every ~30-column span carries
a serial token exactly once (DC-34's discriminator). Turn 1 streams
eight paragraphs; the window is grown to 60×40; turn 2 streams fourteen
more. The terminal's buffer is read back with `history of selected tab`
and every token counted.

```
control (no resize)   66/66   missing 0   duplicated 0
grow   60x24 -> 60x40 60/66   missing 6   duplicated 0     (n=2, identical)
```

The six missing tokens are paragraphs A01–A02, together with the
banner's three labelled lines and the first user chip: the history reads
`kiso 0.20.3` and then `A03S1`. Sixteen rows — exactly the sixteen the
grow added — are gone. Buffers:
`kiso-doc/tui-recon-2026-09-02/e2e-terminal-app/history-grow*.txt`.

## The mechanism

Apple Terminal is bottom-anchored: growing by k rows REVEALS the last k
rows of its scrollback at the top of the screen (measured with no kiso
involved: first visible line 38 → 22 at k = 16, cursor position
irrelevant). Those rows leave the scrollback and become screen rows.

kiso's resize frame reaches back (`all.slice(skip)`, the width is
unchanged) and paints them with identical bytes — harmless. But
`#scrolledOff` is never decreased: the adopt is `max(S, …)` and runs
only on a refold. So for the next k committed rows `leaving = target −
S ≤ 0`, `#emitScroll` emits no line feed, and the window advances by
repaint instead — each advance overwriting the top row on screen, which
is a row the terminal had just pulled back from its history. k rows,
silent, permanent.

On an xterm-class terminal (the VS Code terminal; the emulator behind
`resize.png`) the same code paints a duplicate band instead, because
that class appends blank rows on a grow rather than revealing, and the
rows are still in its scrollback. Same defect, two faces; only the
terminal can say which.

## Why no gate saw it

kiso emits no wrong byte. The rows are destroyed INSIDE the terminal,
by kiso's later frames overwriting what the terminal had restored. A PTY
capture cannot witness it; the A8 gate ("grow the screen and the banner
returns") asserts the reach-back that causes it. The acceptance surface
for this family is the terminal's own buffer, which is why the
reproduction is an AppleScript leg and not a vitest one.

## Resolution

Under R11 route B a settled resize erases the terminal's screen and
scrollback and reprints the session at the new geometry; `#scrolledOff`
restarts at zero and the reach-back has nothing to reach into. The
grow leg (66/66) is one of route B's blocking gates. DC-37's proxy and
the A8 reach-back retire with it.
