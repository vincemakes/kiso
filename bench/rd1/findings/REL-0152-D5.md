# REL-0152-D5 — a resumed session shows nothing

- **id:** REL-0152-D5
- **class:** resume / continuity
- **severity:** P1 — the durability promise is invisible at the moment it
  is supposed to pay off
- **agent:** kiso 0.15.3
- **found by:** owner dogfood, 2026-08-25
- **status:** FIXED, released in 0.15.4

## The behaviour

`kiso resume <id>` (or picking from the picker) prints one line —

```
session 2026-08-25T07-29-29-32d9 (switched — previous: 2026-08-25T08-15-58-9c99,
 /resume 2026-08-25T08-15-58-9c99 returns)
```

— and nothing else. No transcript, no last exchange, no indication of
what the session was about. The user is dropped at an empty prompt inside
a conversation with 6,581 events and 3 turns.

## Why this is P1 rather than cosmetic

The product's whole claim is that a long task survives interruption and
you can come back to it. Coming back currently means **being told the
session exists and shown none of it.** A user who resumes has to
reconstruct from memory what the agent was doing, which is the exact work
resuming was supposed to remove.

It also hides the durable log's real value: the history is right there on
disk — the forensic replay in this round read 6,581 events out of it and
rebuilt the entire screen — and the product does not show the user a
single line of it.

## What it is NOT

Not RD1B-F9 (id aliasing, fixed in 0.15.2) and not REL-0152-D1 (the
frame tearing). This is resume rendering nothing at all, deterministically,
not a paint that goes wrong sometimes.

## Shape of the fix

At minimum, on resume, replay a tail of the durable log into the
scrollback: the last user turn and the assistant's reply, so the user
sees where they were. The projection to do it already exists — the
compositor rebuilds the whole screen from the event stream, which is how
this round's forensics worked.

Open question for the spec: how much tail, and whether a resumed session
should replay into scrollback (native, reflow-safe, matches how kiso
already treats history) or render a bounded summary block.
