# DC-31 — the ask panel never named its finisher, and threw at narrow widths

Status: FIXED in 0.19.1. Found 2026-08-31 in the owner's 0.19.0 dogfood.
Class: three interaction defects and one latent renderer crash, all in
one panel.
Surface: `packages/tui/src/ask-panel.ts`, `packages/tui-cells/src/strings.ts`.

## What the owner hit

They moved the bar to option 1, pressed enter, and nothing happened —
no answer, no advance, no message. Their words, in order: "do I really
have to type 1? that's inhuman design", then, working it out alone,
"I see, it's multi-select; does it only take effect after enter?".

They were not confused. The screen was.

## Four defects

### 1. Enter at rest was a silent no-op

`askKey`'s enter branch read `answered(...) ? advance : { state }`. The
cursor is not a pick, so bar-on-option-1 + enter did **nothing**, in
both modes, with nothing said about it.

The approval panel had already ruled the opposite, in as many words
(TUI2-R3v2 ①): "enter takes the highlighted option… the panel used to
ignore the key every human presses first". So the product carried **two
selection models under one identical bar**, and the owner's transcript
is that trap step for step.

### 2. A digit meant three different things product-wide

- approval / safer: instant commit
- pick panel: moves the cursor, **never** commits
- ask: commits (single-select) or marks (multi-select)

`PANEL_KEYS_ROW`'s own comment claimed its sentence was "true of every
flavor". That invariant broke silently when KC3.5 and TUI2-R2 ④ landed,
and nothing noticed because the comment was the only thing asserting it.

### 3. The digit range was hardcoded

`askAffordance` returned `1-4 pick` whatever the option count was. One
of the repo's own fixtures has **three** options; the row said `1-4`
there for as long as it has existed. REL-0152-D3 fixed exactly this
defect in the input LEAD one function further up, and did not look one
function down.

### 4. A latent renderer CRASH

`askBlockRows` pushed the affordance row **uncut**, unlike the
approval's `cutLine`'d row. Panel rows go through `#checked`, which
THROWS on any row wider than W (invariant ①).

Arithmetic: indent 2 + `1-4 pick · t type · ← back · esc decline` = 42
cells; the question-1 form = 33. **A multi-question ask on question 2 at
W ≤ 41, or any ask at W ≤ 32, killed the renderer.** Nobody had reported
it because nobody had run an ask in a narrow terminal.

## The fix

One selection model for every list — the approval panel's, already
ruled:

- **single**: a digit answers instantly (unchanged); **enter takes the
  bar's row**; space marks; `t` types; esc declines.
- **multi**: a digit marks its row; space marks at the bar; enter with
  anything marked sends the set; **enter with nothing marked marks the
  bar's row and does not send** — the press becomes visible (`◯` → `◉`),
  which teaches the mode in one frame, and the second enter sends.

The row names the finisher and the real count:

```
single  ↑↓ move · ⏎ confirms · 1-N instant · t types · esc declines
multi   ↑↓ move · space or 1-N marks · ⏎ sends the set · t types · esc declines
```

with the DC-2 clause ladder it never had — and the **last standing pair
in both modes is the way through and the way out**. In multi, `⏎ sends`
gives way never: its absence is what caused this finding.

`PANEL_KEYS_ROW` shrinks to what is true of every panel:
`panels: ↑↓ move · ⏎ confirms · digits act on their row · t types`.

## Gates

`packages/tui/tests/r6-d2-ask-panel.test.ts`, 8 gates. Falsifiability
checked by restoring the no-op and the uncut row: the two enter gates
and **the crash gate** go red, and green again when the fix returns —
the crash one is a true red→green over a real throw.

## The lesson worth keeping

**A comment is not an invariant.** `PANEL_KEYS_ROW`'s claim to be "true
of every flavor" was the only thing asserting it, so two rounds could
falsify it without a single gate turning red. Where a comment states a
cross-surface property, either a gate holds it or the comment should say
it is a hope.
