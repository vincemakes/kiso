# DC-40 — kiso's first frame destroys the shell's on-screen history

- **id:** DC-40
- **class:** renderer / how the dock arrives — silent destruction of
  content that was on screen when kiso started
- **severity:** P1 — the shell's prompt, the launch command, and the
  tail of whatever ran before kiso are overwritten, not scrolled; gone,
  not in the scrollback. Strange for a product whose claim is that the
  terminal's scrollback IS the transcript.
- **agent:** kiso 0.20.3 and every version with the REL-0152-R1 diff
  renderer. Older than DC-19/DC-39; the same family.
- **found by:** the R10 assessment (2026-09-02), measuring the installed
  binary in Apple Terminal by the terminal's own buffer. REL-0152-D20
  established the mechanism in 2026-08 and declined the fix.
- **status:** FIXED (R11 Part 1), pending release as 0.20.4. Two
  passes: the first built the planned fix with the feeds AFTER the
  entry reset, passed every house emulator, scored 1/20 on Apple
  Terminal, was reverted, and misread the cause. The second pass found
  the cause (`ESC[r` homes the cursor), moved the feeds BEFORE the
  reset, and measured 60/60 on Apple Terminal.

## The reproduction

Apple Terminal, 60×24. Print 60 lines of shell output, launch kiso, read
the terminal's own buffer (`history of selected tab`). Scripts and
buffers: `kiso-doc/tui-recon-2026-09-02/dc40-probe/` (`order/` is the
second pass), `e2e-terminal-app/`.

```
installed 0.20.3, 60 shell lines:   37/60 survive   (the 37 already in the scrollback)
                  20 shell lines:    1/20 survive
fixed build,      60 shell lines:   60/60 survive
```

Every line that was ON SCREEN when kiso started is lost; only lines that
had already scrolled into the terminal's scrollback before launch
survive.

## The mechanism

kiso's first frame is the full-redraw path with an empty held screen, so
it addresses every row absolutely: `ESC[1;1H ESC[0K … ESC[24;1H ESC[0K`,
painting rows 1..H — the shell's rows. The model assumes its row 0 is
the terminal's row 1, which is true only once a session has scrolled a
screenful; at launch the terminal's rows 1..r are the shell's.

ADR-0046's ghost-spectrum table said the opposite ("sequential emission
from the current position, NO pre-clear") from v6 to 0.20.3. §11 of
design.md: a rule the code contradicts is a bug in one of them; here the
code was the stale one, and the row is corrected with this fix.

## The fix — H line feeds, and why their position is the whole fix

Before the first frame, emit `\n` × H from wherever the shell left the
cursor. From row r that moves H−r rows and then scrolls exactly r: the
shell's rows 1..r enter the scrollback as content (at most one blank row
— the cursor's own line), the screen is blank, the cursor is on row H,
and the model's assumption is true by construction. The count does not
depend on r, so nothing is asked of the terminal. Nothing else in the
compositor changes.

**`ESC[r` (DECSTBM) homes the cursor.** VT100 semantics, honoured by
Apple Terminal (measured: a marker written after `ESC[r` lands on row 1),
xterm, xterm.js and tmux. The entry reset (REL-0152-D19) opens with
`ESC[r`. Feeds emitted after it therefore start from row 1, move H−1
rows and scroll ONE — the shell's row 1 survives, the frame paints over
the other nineteen. That is the 1/20.

Isolation on the real terminal, each replayed after 20 echoes, same
frame bytes throughout (`dc40-probe/order/`):

| bytes | survive |
|---|---|
| reset, 24 feeds, frame — the first build | 1/20 |
| **24 feeds, reset, frame — the fix** | **20/20** |
| `ESC 7`, reset, `ESC 8`, 24 feeds, frame | 20/20 |
| `ESC[r` then a marker | marker on row 1 |

The fix as shipped (`compositor.ts`, the `#needsReset` block):

```
\n × H                                  the shell's rows scroll away as content
ESC[r ESC[?69l ESC[?7h ESC[?25l         the D19 reset — homes the cursor, harmlessly now
ESC[?7l … ESC[1;1H ESC[0K …             the frame, absolute as before
```

The reset still precedes the frame, which is D19's contract (a frame
drawn into an inherited sub-region is the defect); only the feeds run
under whatever scroll region the shell left. A region a killed foreign
program left set makes the feeds scroll that region alone and the frame
paint over the rows outside it — what every frame did before this fix,
never worse. The `ESC 7`/`ESC 8` variant would cover that case too and
was not taken: two more escapes at boot for every emulator and needle
in the repo to learn, for a case kiso itself can never cause.

## What the first pass got wrong, and why it matters

The first pass's isolation table was accurate; its reading was not. It
concluded that absolute cursor addressing on a freshly-scrolled screen
"pulls scrollback back" and that `ESC[r` is "destructive by itself", and
proposed a CUP-free first frame (the reference implementation's shape)
as the only fix. Every row of its table is explained by the homing
alone:

- reset + 24 feeds, no frame → 20/20: nothing painted, nothing lost.
- + the frame's first `ESC[1;1H` → 19/20: the shell's prompt, printed
  after the replay, landed on row 1 over one shell line.
- + eleven `ESC[n;1H ESC[0K` → 9/20: eleven rows erased.
- `ESC[r` + a CUP-free append → 11/20: the append started from the
  homed cursor and wrote nine rows of text over shell lines.
- a CUP-free append without `ESC[r` → 20/20: it started from the
  shell's cursor.

Row 2 of the table above refutes the reading directly: the same
absolute-addressed frame, the same reset, 20/20 once the feeds come
first. The fix stays the three-line change the plan approved; the
first-frame emission is not rewritten.

## Why the emulators passed the wrong order

Every house emulator (VtScrollback, Screen, WideScreen, VtScreen)
stripped `ESC[r` as a no-op, so a homed cursor was modelled as a cursor
that had not moved, and feeds after the reset scrolled r rows in the
gate and one row on the terminal. The gate agreed with the code and both
were wrong together — REL-0152-D20's trap, met a second time.

VtScrollback now models the homing, and the DC-40 gate carries a
DISCRIMINATOR: the shipped bytes with the feeds moved after the reset
lose 19 of 20 shell rows in the emulator, exactly as on the terminal.
The gate is red on the order that was built first. The acceptance
surface for this class remains the real terminal's own buffer, read by
AppleScript; the emulator gate is the discriminator that would have
caught the first pass, not a stand-in for the terminal.

correct there, and the DC-40 feeds are what a half-reprinted terminal
gets scrolled away by at the next launch.

opening scrolls the shell's screen away first; it is one scroll up, not
