# DC-27 — liveCount() measures a screen the projection no longer draws

Status: FIXED in R4 (2026-08-30). Found in the R4 design review,
against 0.17.0. `liveCount()` now returns the projection's own row
count at the same content cap the force-commit loop applies; gated by
`packages/tui/tests/r4-act-slot.test.ts` ("R4 E").
Class: gates asserting a fiction. No user-visible defect today.
Surface: `packages/tui/src/compositor.ts:1970-1979`.

## The defect

`liveCount()` is the live region's scalar — the number the cap tests and
the KC1 geometry tests assert against. Its non-panel branch is a plain
loop over every live cell:

```js
for (let i = this.#committed; i < this.#cells.length; i += 1) {
    const rows = cellComponent(this.#cells[i]!).render(W, ctx);
    lines += this.#space(i, prev, rows).length;
    prev = rows;
}
```

It does not call `#liveProjection` (:1850) and does not implement any of
what R3i taught the projection:

- no open-segment check — a stretch's cells are counted individually
  instead of collapsing to the one stretch line;
- no flight rule — the projection skips a DONE cell inside the open
  segment (:1874); this loop renders it in full;
- no `LIVE_ACT_HEADS` budget, no `+N more running` row.

So for an open stretch with five completed calls, `liveCount()` counts
roughly five four-row blocks the screen does not contain.

## Why nothing is visibly broken

The force-commit loop does not consume this scalar — it measures
`liveLines.length`, taken from the projection itself. The screen is
correct. Only the tests are wrong, and they are wrong in the CONSERVATIVE
direction (the scalar over-counts, so a cap assertion that passes would
also pass against the true number).

That is exactly what makes it worth a finding rather than a shrug: the
gates that are supposed to catch a cap regression are currently proving a
property of a function nothing renders from. A real regression in the
projection's height would not move this number at all.

## The doctrine it violates, stated in the same file

The sheet branch twelve lines above carries the rule, in a comment
(TUI2-R1 D):

> the sheet occupies the live region, exactly like the panel — the scalar
> must say so, or the cap arithmetic disagrees with the screen.

The non-panel branch is the case that rule was written for, and it is the
one that drifted.

## Remedy

Rebase `liveCount()` on `#liveProjection` — one projection, counted, plus
the chrome terms it already adds. Then re-derive the assertions in
`packages/tui/tests/compositor-kc1-geometry.test.ts` and
`packages/tui/tests/compositor.test.ts` against the true numbers, each
flipped assertion carrying the declared-supersession comment.

This must land WITH any change to the live region's height (the R4 C3
slot), not after it: shipping a height change while the scalar still
measures the old shape would leave the round with no gate that can see
what it did.
