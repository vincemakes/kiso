# DC-33 — a mid-turn resize: what is by design, and what is not checked

**Status**: CLOSED — the reflow is the contract; the duplication was
not ours, measured. A gate for the gap now exists.
**Reported by**: the owner, from a screenshot of a live 0.20.0 session
**Round**: R8b, 2026-09-01

## What was seen

Widening the terminal during a turn: only the LOWER part of the
content reflowed to the new width. Everything above kept the fold it
was printed with. And — in the same screenshot — a passage of prose
appeared TWICE, once folded narrow and once folded wide.

## Half one: the reflow is the contract, not a defect

A row that has entered the terminal's native scrollback is ink. kiso
never re-emits it, never reflows it, never erases it (ADR-0046, and
design.md §7.1). Only the live region — the current thinking, the
activity block, the composer — is repainted every frame, so only it
can take a new width.

This is visible WITHIN one turn because kiso commits as it goes: by
the time a turn is a few tools old, most of it is already ink.

`/rewrap` exists for exactly this and does the only thing the contract
permits: it APPENDS a re-folded copy of the recent prose at the
current width. It cannot rewrite what is above.

## Half two: measured — the resize scrolls nothing of ours

A line feed is the ONLY way a row of ours enters the terminal's
scrollback. So the question has a byte answer, and the compositor
already states the claim in its own words (REL-0152-R1: "a resize
scrolls NOTHING of ours"). Driven through a real PTY, a turn that
commits a screenful of prose and then holds itself open on a slow
shell, with the winch landing mid-turn:

```
before the winch   7518 bytes   LF = 17     <- rows really were committed
after  the winch   6962 bytes   LF =  0     <- nothing entered history
```

The markers do appear twice in the post-winch bytes, and that is the
repaint: with zero line feeds they are cursor-addressed rows painted
in place, which is what a repaint at a new width IS.

So the second copy the owner saw was not ours. Three things stacked:

1. the committed rows above kept their fold — the terminal does not
   reflow its own scrollback (Terminal.app does not; some others do
   optionally), and kiso cannot;
2. the live region below did take the new width, because it is
   repainted every frame;
3. the model was repeating itself — that session ran the same `curl`
   three times with three different durations and produced the same
   sentence more than once. The second copy landed after the resize,
   so it was folded wide, which is what made it look like a reflow.

## The gap that was real, and is now closed

Nothing gated a resize DURING a turn. `tui-v4-reflow` and
`tui-v6-resize-idempotence` both resize an IDLE session after the turn
completes; `tui-v7-flow-contract`'s W9 resizes for real but counts
FRAMES, not content. A resize that repainted once and duplicated
content would have passed all three.

`apps/cli/tests/dc33-resize-midturn.test.ts` is that case. It asserts
the pre-winch commit count first, so the run cannot pass by never
reaching the state it is about — mutating that bound turns the case
red at 17, which is the number of rows actually committed.
