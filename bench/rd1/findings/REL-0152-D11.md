# REL-0152-D11 — an image cannot be pasted into the composer

- **id:** REL-0152-D11
- **class:** missing capability / input
- **severity:** P2 — a routine expectation of a modern coding agent
- **agent:** kiso 0.15.4
- **found by:** owner dogfood, 2026-08-25 (twice)
- **status:** FIXED, and the open question is ANSWERED. The clipboard
  coercion that fails from a detached shell SUCCEEDS inside a real
  terminal session — the owner pasted a screenshot and kiso attached it.
  The last defect on that path was [[REL-0152-D16]] (the temp path went
  to the slash-command parser), fixed in 0.15.9.

## What is already built

The wire carries images end to end. This is the useful part of the
finding: the work is smaller than it looks.

- `packages/core/src/protocol/messages.ts` defines an image ContentBlock
  (base64 or url, four media types).
- `packages/provider-anthropic/src/index.ts:263` sends it.
- `packages/provider-openai/src/index.ts:342` sends it as `image_url`
  with a data URI — so the OpenAI-compatible family carries it too.
  (Tool RESULTS remain text-only there, by that adapter's own note.)

## What is missing

Exactly one thing: nothing in the CLI ever constructs an image block.
`grep 'type: "image"' apps/cli/src packages/runtime/src` is empty. The
gap is entirely on the input side.

## What was built

A turn's text is scanned for references to image files and each one
becomes an image block beside the words. `session.run()` was widened to
accept content blocks — the parameter that had narrowed the whole
feature out of existence.

The reference is a PATH, deliberately, because two things a user can
already do produce one on any terminal with no clipboard involved:
dragging a file into the window, which terminals answer by inserting its
path, and typing or pasting a path.

Rules, each with a case:

- a turn with no reference returns the STRING unchanged, so every
  request that is not about an image is byte-identical to before;
- the words are kept, in place — a turn is "what is wrong here?" plus
  the screenshot, and the question is half of it;
- the media type comes from the file's BYTES, not its name (a screenshot
  saved as `.jpg` is very ordinary);
- a path that is missing, unreadable, not an image, or over 5MB is left
  standing as text. Silently dropping it would tell the model about a
  file it cannot see, which is worse than telling it nothing;
- quoted paths survive, because that is what a terminal inserts for a
  name with a space in it.

### Proven to the wire, not to the unit boundary

The claim is that the MODEL receives the image, and between the block
and the model sit the durable event, the projection, and an adapter —
each written to carry an image and none of which had ever carried one.
So the gates drive the real path and assert on what each provider would
be sent:

- the projection produces a user message whose content is the blocks;
- the OpenAI-compatible adapter's request carries
  `image_url: { url: "data:image/png;base64,…" }`;
- the Anthropic adapter's request carries an `image` block whose
  `source.media_type` is `image/png`.

## The clipboard route, built

Reuse the D8 capsule, which is already the right shape:

1. On paste-end, if the collected run is EMPTY and the platform can
   report a clipboard image, read it.
2. Write it to a session-scoped temp file, hold it beside the paste map,
   and put `[Image #1 png 201KB]` in the buffer — a capsule like any
   other, editable and deletable, and deleting it drops the image.
3. At submit, the CLI splits the line on image tokens and builds the
   ContentBlock array the protocol already accepts, instead of the plain
   string it builds today. This is the one real change: `onLine` hands
   over a string, and it has to hand over content.

## The unresolved question — measured, not guessed

The clipboard read is NOT proven. On this machine `osascript -e
'clipboard info'` correctly reports the flavors present (a 201KB
`«class PNGf»` while an image was on the clipboard), but coercing the
data — `the clipboard as «class PNGf»`, and `as TIFF picture` — fails
with error -1700 from a detached shell. That is consistent with promised
(lazily-rendered) clipboard flavors, which the source app materializes
only for a process in the right session context.

kiso runs in the user's real terminal session, where it may well work.
Nobody has tested it there, and the round must start by testing it there
rather than by writing the feature on top of an assumption. If it fails,
the fallbacks are a small native helper or reading the pasteboard
through a bundled binding — both real costs that belong in the spec.

## Also for the spec: the model may not accept images

The owner is running `deepseek-v4-flash`. The adapter will send the
block; whether that model accepts one is a separate question. Whatever
the answer, a paste that cannot be delivered must SAY so at paste time —
attaching an image the model will silently drop is worse than refusing
it.
