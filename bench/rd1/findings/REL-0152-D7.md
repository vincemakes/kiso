# REL-0152-D7 — a committed user chip is erased by the live band

- **id:** REL-0152-D7
- **class:** renderer / erase range
- **severity:** P1 — content the user typed disappears from the screen
  permanently, deterministically
- **agent:** kiso 0.15.3 and earlier
- **found by:** owner dogfood 2026-08-25, then reproduced
- **status:** OPEN. Self-contained red test:
  `packages/tui/tests/chip-loss.test.ts`

## The behaviour

The owner typed a message. It never appeared as the black-on-white user
chip every other message renders as, and they reasonably concluded the
input had been swallowed.

It had not. The chain, measured one link at a time:

| link | verdict |
|---|---|
| the runtime received it | ✅ `seq 4386` in the durable log, complete |
| the compositor emitted it | ✅ replaying the session emits it 10 times |
| a correct terminal keeps it | ❌ **it is not on the final screen** |

The third link is this finding. A terminal that applies every byte
faithfully still ends up without the chip, so this is not a paint-timing
problem and **frame atomicity cannot fix it**.

## Where it goes

Replaying the owner's session (2026-08-25T07-29-29-32d9, 6,581 events)
through the real `Body` into the A7 cell model, tracking the chip after
every event:

```
#3074 APPEARS  (user_input)    the chip reaches the screen
#3075 GONE     (thinking)      the next thinking frame erases it
#3496 APPEARS  (tool_result)
#5067 GONE     (text_delta)    the streamed answer erases it for good
```

**Both losses land exactly when the LIVE band grows.** The chip is
committed content: it belongs to the frozen band and the scrollback, and
an erase range meant for stale live copies is reaching past its boundary
into it.

## The same miscalculation, seen from the other side

In that session the FIRST user chip ends up on the screen **17 times**.
Erasing rows that should have been left alone and repainting elsewhere
loses content in one place and duplicates it in another — the A7 / A8 /
A8b family the compositor's own comments document at length.

Any fix must be judged on both counts. A change that keeps the third
chip while leaving the first duplicated seventeen times has moved the
bug, not removed it.

## Reproduction

`packages/tui/tests/chip-loss.test.ts` — no dependency on the owner's
machine. A 24-row terminal, one turn committed deep enough to move the
window, then the chip, then a thinking burst and a streamed answer. The
transition sequence matches the real session exactly:

```
real session:  APPEARS@user_input  GONE@thinking  APPEARS@tool_result  GONE@text_delta
minimal repro: APPEARS@chip        GONE@thinking  APPEARS@stream       GONE@stream
```

## The frame autopsy — where to look next

Capturing the killing frame and parsing its `CUP … EL` pairs against the
chip's screen row:

```
GONE@thinking   chip at row 20, that frame erased [20],           LFs=0
GONE@stream     chip at row 17, that frame erased [17,18,19,20],  LFs=0
```

**No scroll occurred (`LFs=0`) and the chip's own row was erased.** The
erase begins AT the chip and runs downward, so a range that should start
below the committed content is starting inside it.

Two candidates were tested and ruled out by experiment, not by reading:

- the **stale-rows** range (`staleFrom`, compositor.ts:2040). Changing
  its origin from `committed.length` to `leaving` — which its own comment
  argues for — did not move the repro, and left the suite at 733/734.
- the **overlap** range (`overlapFrom`, compositor.ts:1968). It only runs
  when `committed.length > 0`; both losses here happen with no commit.

That leaves the **gap erase** (compositor.ts ~2029), which blanks
`liveTop + liveLines.length … H − 4 − inputExtra − queue − menu`. If
`liveTop` is computed lower than the committed band actually extends,
the gap starts on top of committed rows — which is exactly the observed
shape: erasure from the chip's row downward, with nothing scrolling.

That instrumentation was done, and it ruled the gap out too — and found
the actual cause.

## Root cause: the window moves without scrolling

Probing `liveTop`, the gap bounds and the scroll bookkeeping at every
frame of the repro:

```
gap=[21..20]  liveTop=20 liveLines=1 committedThisFrame=0 skip=5  leaving=0
gap=[21..20]  liveTop=19 liveLines=2 committedThisFrame=0 skip=6  leaving=1
gap=[21..20]  liveTop=18 liveLines=3 committedThisFrame=0 skip=9  leaving=2
gap=[21..20]  liveTop=17 liveLines=4 committedThisFrame=0 skip=10 leaving=1
```

**The gap range is empty** (`21..20` emits nothing), so no erase range is
responsible. What erases the chip's row is the LIVE BAND'S OWN WRITE:
the band is painted at `liveTop … liveTop + n − 1`, each row with an
`EL`, and `liveTop` walks UPWARD — 20, 19, 18, 17 — straight over rows
that hold committed content. The `[17,18,19,20]` in the autopsy is that
write, not a cleanup.

The reason it may do so is the last column: **`leaving` is non-zero while
`committedThisFrame` is zero.** `leaving` means the window moved, and the
rows it moved past must be carried into the scrollback by real LFs. But
the scroll that does that lives inside `if (committed.length > 0)` —

```js
if (committed.length > 0) {
    …the leaving pre-paint and the LF scroll…
}
```

so on a frame that moves the window WITHOUT committing a line, the block
is skipped entirely: no LFs are emitted (`LFs=0` in the autopsy), the
departing rows never reach the scrollback, and the growing live band
simply overwrites the committed content in place.

That is the whole defect, and it explains both symptoms at once. Content
overwritten instead of scrolled is **lost** (the third chip, 0 copies).
Content re-painted at a new row while an old copy was never carried away
is **duplicated** (the first chip, 17 copies).

## The fix is not a one-line move

Hoisting the scroll out of the `committed.length > 0` guard is the
obvious shape. **It was attempted, three times, and reverted.**

| attempt | repro | rest of the suite |
|---|---|---|
| emit `leaving` LFs when nothing commits | **green** | A7 `4 copies at 60x20`, greeting twice at 40x24 |
| + pre-paint the departing rows first (the A8b shape) | green | same two failures |
| + EL the rows the repaint re-draws (A7 single-copy) | green | same two failures |

Every attempt fixed the loss and produced DUPLICATION in its place — the
other half of the same defect, moved rather than removed. That is the
outcome this finding predicted and the reason the section header says the
fix is not a one-line move.

What the attempts establish, and what the next round should start from:

- **the diagnosis is right** — emitting the missing scroll does make the
  chip survive, in the repro AND without breaking 731 of 733 tests;
- **the scroll alone is not enough.** The commit path pairs its scroll
  with a pre-paint written in terms of the committed sequence and an EL
  pass that enforces the single-copy discipline. Both were transcribed
  for the no-commit case and neither removed the duplication, so the
  no-commit path's correct pre-paint is NOT simply the commit path's with
  `committed` swapped for `liveLines`;
- **the two A7/R2pre cases are the real acceptance**, not the repro.
  A change that greens `chip-loss` while leaving those red has moved the
  bug to where the older gates can see it — which is at least honest, but
  it is not a fix.

The next attempt should model what SHOULD be in the scrollback after a
window move with no commit, and derive the pre-paint from that, rather
than adapting the commit path's code by substitution.

## Relationship to the other renderer findings

- **REL-0152-D1** (the tear) is a different defect: frames are too big
  and not atomic, so a terminal without DEC 2026 paints them half-done.
  It is transient and cosmetic. D7 is deterministic and destructive.
  **D7 should be fixed first**, and the cell-diff work D1 needs must not
  be started until D7 is out of the way, because a diff built over a
  wrong erase range would preserve the wrongness more efficiently.
- **REL-0152-D5** (resume shows nothing) is separate again.

## What must not happen

The compositor's erase ranges are the most accident-prone code in the
tree — its comments record at least five past incidents, each of the
form "a row number stopped meaning what it meant". Any fix lands with
the full compositor and A7 suites green, the two counts above asserted,
and the owner's own Terminal.app check.
