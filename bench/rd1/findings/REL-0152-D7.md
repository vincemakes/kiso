# REL-0152-D7 — a committed chip is painted over by the live band and never reaches the scrollback

- **id:** REL-0152-D7
- **class:** renderer / content loss
- **severity:** P1 — a message the user sent disappears with no trace
- **agent:** kiso 0.15.3
- **found by:** owner dogfood, 2026-08-25 ("this message got swallowed")
- **status:** FIXED by [[REL-0152-R1]], the cell-diff renderer, released
  in 0.15.8. The gate in `packages/tui/tests/chip-loss.test.ts` went from
  `it.fails` to a plain `it` in the same commit, and the owner confirmed
  it on their own machine: messages are no longer swallowed.

## The behaviour

A user chip reaches the screen for one frame and is gone at the next.
Forensics on the owner's session (2026-08-25T07-29-29-32d9, 6,581 events)
replayed through the real compositor and the A7 cell model:

```
#3074 APPEARS  (user_input)   the chip reaches the screen
#3075 GONE     (thinking)     the next thinking frame erases it
#3496 APPEARS  (tool_result)
#5067 GONE     (text_delta)   the streamed answer erases it for good
```

It ends in no scrollback and on no screen. The same session shows the
mirror symptom: the FIRST chip is on the screen 17 times.

## The mechanism (established)

Three facts, each measured on the replay:

1. **The window's top follows the live band, not just the commits.**
   `skip = committedLines + liveLines + chrome − H`. A streaming turn one
   line taller moves the window with nothing committed.
2. **The steady path scrolls one LF per COMMITTED line.** So a frame that
   moves the window without committing scrolls nothing, and then paints
   the taller band at a `liveTop` one row higher — over the bottom of the
   frozen band. Instrumented death of the chip: `liveTop 21→20,
   erased=[20], LFs=0`.
3. **Nothing is lost at that moment.** The row is displaced, and a later
   shrink takes the full-redraw path, which repaints every row at its
   model position and brings it back. The loss happens when the LFs
   arrive: the scroll carries the top `committed.length` rows of the
   SCREEN into the scrollback, and one of them is the live band's
   leftover, not the committed row it displaced.

## Why the obvious fixes do not work

Five attempts, each measured against the A7 replay and the TT-1B
scrollback replay:

1. **Scroll `leaving` in the no-commit branch.** Fixes the chip. Breaks
   A7 at 40x24 frame 106: the window move is REVERSIBLE — the band
   collapsing to a fold slides the window back down over rows already
   scrolled — so the greeting lands in the scrollback and on the screen.
2. **Scroll `leaving` in both branches.** Same failure, earlier.
3. **Hand the no-commit frame to the full path.** Fixes the chip, fixes
   40x24. Leaves 40x12 frame 230: a previous full repaint had displaced
   the screen top, so the next frame's LFs carried off rows the repaint
   then drew again.
4. **A monotonic "scroll floor" driven only by the committed height.**
   Fixes the chip, A7 and TT-1B, but breaks the frames where the model
   still FITS on screen: the dock is pinned to the terminal's bottom row,
   so every committed line must scroll whether or not anything leaves the
   window. The floor scrolls nothing until the screen is full.
5. **Scroll by the model's total growth.** The correct invariant for a
   bottom-anchored dock, and it agrees with the commit count on exactly
   the frames that made the commit count look right — but it over-scrolls
   while the model still fits, where the layout wants no movement at all.
6. **Stage the scrolling rows from the model before the LFs.** Fixes the
   chip and changes no scroll count, but re-emits rows at 1..N on every
   commit frame, which the emit-exactly-once gates forbid.

## What this says about the design

The steady path moves the frozen band by scrolling it, and scrolling is
irreversible. The window is bottom-anchored and therefore moves BOTH
ways. Those two cannot both be true for a band whose height varies, and
every patch above is an attempt to have them both.

The resolution is the one REL-0152-D1 already names: a full screen buffer
diffed cell by cell, whose correctness comes from HOLDING a copy of the
screen rather than from remembering what was written. A renderer that
holds the screen does not have to decide whether a window move is
reversible — it computes the difference and emits it. That is the 0.15.4
architecture round, and D1 and D7 are the same round.

## Closed — 2026-08-26

Six fixes were built and reverted against this finding (one for the
tear, five for the chip), and every one of them traded the loss for a
duplicate somewhere else. They were all attempts to make the renderer's
MEMORY of what it had written agree with the terminal.

REL-0152-R1 is what held: the compositor HOLDS the screen and emits the
difference. A renderer that holds the screen cannot disagree with
itself, so a row that is wrong for any reason is repaired by the next
frame — which is the thing none of the six patches could say.

The owner's verdict on 0.15.8, in their own words: messages are no
longer swallowed.
