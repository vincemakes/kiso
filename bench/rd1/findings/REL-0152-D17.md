# REL-0152-D17 — the brackets were kiso's own stderr, and my instrument could not see it

- **id:** REL-0152-D17
- **class:** renderer / a second writer on the same terminal
- **severity:** P1 — visible corruption that survives a whole session
- **found by:** an external consult (fable, at the owner's suggestion),
  reading evidence I had already gathered
- **status:** FIXED

## The conclusion I got wrong, three times

REL-0152-D1's stray `[` and `]` were chased across three rounds. Each
time I measured the byte stream, found it clean, and concluded the
terminal was inventing the characters. The final form of that reasoning
was:

> kiso emits no OSC and no bare `]`. A `]` on screen cannot have come
> from its stream. Therefore the terminal makes it.

The first two sentences are true and the conclusion does not follow. The
sound conclusion is **therefore something ELSE wrote it** — and the
something else is kiso, on the other file descriptor.

`console.error` writes to fd 2, the same tty, and several of kiso's
notices begin with `[` and contain `]`:

```
[extensions] …            [project .kiso] …
[KISO_FAUX_SCRIPT] …      [run failed] …
[kiso] approval policy … threw … — degraded to ask
```

Subagent children are spawned with `stdio: [..., ..., "inherit"]`, so
their stderr reaches the same terminal too.

## Why my instrument agreed with me

`KISO_TRACE_BYTES` wrapped `process.stdout.write`. Only that. So the
capture taken to prove "the bytes leaving kiso are clean" **could not
see the bytes that were not clean.** It supported the conclusion by
being blind to the counter-evidence, which is the worst thing an
instrument can do — worse than no instrument, because it converts a
guess into a measurement.

## Why it survives, and why only on the box

REL-0152-R1's held-screen renderer writes only rows that differ. It
guarded stdout, so an outside write there forgets the screen and the
next frame repairs it. Nothing guarded stderr, so a `[extensions] …`
line landed on the tty and the renderer never knew.

The residue therefore persists on exactly the rows whose desired content
NEVER changes — the composer box's `╭──╮` and `╰──╯`. That is precisely
where the owner sees it: a `[` at the left edge and a `]` at the right,
for the whole session, clearing on a resize (the one full repaint) and
returning on the next launch.

It also explains what nothing else did:

- **the competitor's immunity** in the same terminal, at the same width,
  with the same locale — the second stream belongs to kiso's process;
- **the repeated boot banner**, all under one session id: every external
  newline at the bottom row scrolls one more copy into the scrollback,
  and ONLCR makes each `\n` a CRLF;
- **`[session 2026-…`** — a printable `[` processed after an `ESC[0K`
  left the cursor at column 1 and before the row's own text, which is
  an interleave fossil and not an escape-parsing artifact. An
  ESC-loss theory predicts litter like `[0Ksession`, which was never
  observed.

## The fix

The guard covers BOTH descriptors. A compositor cannot hold a belief
about a terminal it does not own: any write it did not make forgets the
screen, whichever descriptor carried it. Not a list of writers to
remember, and not silencing the loggers — new callers cannot get it
wrong because they are not asked to get it right.

`KISO_TRACE_BYTES` now records stderr as well, tagged `err`, and
`scripts/trace-brackets.mjs` reports those writes first.

## The lesson

Two, and the second is the expensive one.

1. An instrument that can only see the places you already believe are
   clean will confirm you. Trace every path the thing under test can
   take, or state plainly which paths the capture does not cover.
2. "It cannot have come from X" narrows the field; it does not name the
   answer. I turned an elimination into an identification and stopped
   looking, across three rounds, while the writer sat in the same
   process behind a descriptor I had not thought about.
