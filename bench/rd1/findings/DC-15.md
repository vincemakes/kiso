# DC-15 — the thinking fold crashes the TUI below eleven columns

- **id:** DC-15
- **class:** width arithmetic / invariant ①
- **severity:** P2 — a crash, at a width nobody uses
- **agent:** kiso 0.16.3 (introduced by the R2 fold rewrite)
- **found by:** sweeping `ThinkingFold.render` across W=1..120 and
  measuring the visible width of every row
- **status:** FIXED (0.16.4 working tree)

## The measurement

```
W=  2  visible=11   OVERFLOW
W=  5  visible=11   OVERFLOW
W=  8  visible=11   OVERFLOW
W=  9  visible=11   OVERFLOW
W= 10  visible=11   OVERFLOW
W= 11  visible=11   ok
```

Eleven cells at every width below eleven. Invariant ① does not
truncate — it **throws**, and the throw kills the compositor.

## The cause

Two independent floors that cannot both be satisfied:

```ts
const room = Math.max(1, W - 2 - tail.length - 1);   // floors at 1
const pad  = Math.max(1, W - 2 - visibleWidth(cut) - tail.length); // floors at 1
```

`2 (gutter) + cut (≥1) + pad (≥1) + 6 ("/think")` = 10 minimum, and
`wordCut` returns `room + 1` when it has to append its ellipsis to a
one-cell cut — so 11. The width never enters the sum once both floors
engage.

The retired code was safe to W=2 because it had no reserved tail. The
comment four lines above the defect records that the previous
invariant-① crash in this same cell was "still live on npm" when it was
found, which is the argument for the belt below rather than for
arithmetic that has to be re-proved whenever a span moves.

## The fix

Two changes, and the second is the one that matters:

1. Below the width where the affordance and one word of content can both
   stand, the affordance is **dropped**. A row that cannot hold the
   key's name has nothing to say about the key.
2. Both returns go through `cutLine(row, W)` — SGR-aware, single-row.
   The invariant now holds by CONSTRUCTION rather than by arithmetic.

Swept W=1..120: no row exceeds W.

## The same class, two rows over

`bannerLines`' name row was the one row in that function pushed without
a width guard (`kiso 0.16.4` = 11 cells, thrown at W ≤ 10 **at
startup**), and `truncateRow` floored its cut at 0 and then appended a
six-cell ` (+N)` marker regardless — so every width ≤ 6 returned a row
wider than the terminal. A marker wider than the row it marks is not a
marker. Both fixed; the same 1..120 sweep covers them.
