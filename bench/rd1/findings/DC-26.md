# DC-26 — launched in $HOME, kiso cannot find the project it IS

Status: OPEN. Raised 2026-08-30 by the owner, against 0.17.0.
Class: orientation gap (no user-level instruction layer), plus four
aggravators. Not a renderer issue.
Evidence: `~/.kiso/sessions/2026-08-30T07-38-37-c07a.jsonl`, the run whose
second user input is "review the current project". 31 tool calls.

## The observation

Asked to review the current project, the agent found the kiso codebase on
**call 15**, after asking the owner **twice** where it was — the second
time the owner had to type the path by hand. The reference implementation,
run against the same machine and the same question, reached it without
searching.

## What actually happened (from the log, in order)

kiso was launched from `/Users/vinve`. `workspaceRoot` is `process.cwd()`
(`apps/cli/src/index.ts:524`), so the workspace WAS the home directory.

| # | call | outcome |
|---|---|---|
| 1 | `list_dir {}` | home — 81 entries, **62 of them dot-entries** |
| 2 | `read_file package.json` | `~/package.json` exists: `{"devDependencies":{"@vincemakes/kiso-code":"^0.1.16"}}` |
| 3–5 | `list_dir` KisoWork / hutch-parallel / uooki_workspace | wrong trees; KisoWork is empty |
| 6 | `shell find . -maxdepth 3 -name .git -type d -not -path "*/.*"` | **(no output)** |
| 7 | `shell find . -maxdepth 2 -type d …` | lists `./Desktop`; cannot reach depth 3 |
| 8 | **`ask_user`** "which project should I review?" | owner answers "kiso" |
| 9–11 | `list_dir .kiso`, `read_file .kiso/config.json`, `list_dir .kiso/sessions` | kiso's own CONFIG dir, not its source |
| 12 | **`ask_user`** "which project's code exactly?" | owner types "the kiso under devv" |
| 13–14 | `find -iname "*devv*"`, `list_dir Desktop/devv` | closing in |
| 15 | `list_dir Desktop/devv/kiso` | **found** |
| 16–31 | package.json, git log, CLAUDE.md, TODO.md, typecheck, test:unit, size | the actual review, and it was competent |

Once oriented the agent did fine. Everything wrong happened in calls 1–14.

## Root cause

### R1 — the document that answers the question was never read (the binding one)

`~/.claude/CLAUDE.md` exists on this machine, 3301 bytes, and its line 5
states in plain words that `~/Desktop/devv` holds seven projects, kiso
among them. The answer was sitting on disk the whole time.

kiso never read it. `readProjectInstructions` (`apps/cli/src/index.ts:385`)
reads `AGENTS.md` then `CLAUDE.md` **from cwd only**:

```js
const INSTRUCTION_FILES = ["AGENTS.md", "CLAUDE.md"] as const;   // :376
for (const name of INSTRUCTION_FILES) { readFileSync(join(cwd, name)) … }
```

`~/AGENTS.md` and `~/CLAUDE.md` are both absent, so kiso got nothing.
**There is no user-level instruction layer in kiso at all** — no
`~/.kiso/CLAUDE.md`, no `~/.kiso/AGENTS.md`, no equivalent of any kind.
The project layer exists; the user layer was never built.

The reference implementation reads a user-level file. That is the whole of
"it found kiso in one shot": it did not search better, **it already knew**,
because the owner had written it down and it was reading what the owner
wrote.

### R2 — a decoy manifest in $HOME

`~/package.json` declares a dependency on `@vincemakes/kiso-code@^0.1.16`.
Call 2 reads it and it looks exactly like a project root. The model
anchored on a false answer at its second call — and on a version eight
months stale, which would have poisoned the review had it not eventually
recovered.

### R3 — kiso never says "there is no project here"

Launched in a home directory, with no VCS root, no workspace manifest that
matches, and no instructions found, kiso proceeds in silence as though home
were a workspace. Nothing in the banner, the prompt, or the first frame
tells the model — or the owner — that the workspace it was handed is not a
project. The failure is silent, which is why it cost fifteen calls.

### R4 — `.kiso` is both our config dir and the product's name

Calls 9–11 went into `~/.kiso/` and found `config.json` and `sessions/`.
Told to look for "kiso", the model found a directory named exactly that
and burned three calls proving it was the wrong one. Our own state
directory is a trap for the search we most want to succeed.

### R5 — the two read tools disagree about dot-entries

`list_dir` SHOWS dot-entries — 62 of the 81 lines in call 1 were noise
(`.DDLocalBackups/`, `.Trash/`, `.android/`, `.bash_history`, …).
`search_text` HIDES them (`packages/tools-node/src/index.ts:522` skips
every `entry.name.startsWith(".")`, which also makes `.github/workflows/*`
unsearchable). Opposite rules, same tool set, neither documented, neither
chosen on purpose as far as the code shows.

## Correction — what the first draft of this finding got WRONG

Recorded so the error is not repeated. The first draft claimed the system
prompt's steering ("search with search_text, never shell grep/rg", "list
with list_dir, never ls" — `packages/runtime/src/compose.ts:19-24`) had
closed the shell escape hatch and stopped the model from running `find`.

**The log falsifies that.** Calls 6, 7 and 13 are all `shell find`. The
steering did not block anything. The finds failed on their own merits:

- call 6's `-not -path "*/.*"` excludes every path with a dot component —
  and `.git`, the thing it was searching for, is one. The command excluded
  its own target and returned nothing.
- call 7's `-maxdepth 2` cannot reach `Desktop/devv/kiso`, which is at
  depth 3.

The missing glob tool is a real gap, but it was NOT the binding constraint
here and is de-scoped from this finding. The prompt's self-contradiction on
grep (`apps/cli/src/index.ts:360` says shell is for "builds, tests, git,
grep"; `compose.ts:21` says never shell grep) is real and still worth
fixing, but it did not cause this.

## Proposed remedies — NOT implemented, awaiting a ruling

1. **A user-level instruction layer.** Read `~/.kiso/AGENTS.md` then
   `~/.kiso/CLAUDE.md` before the cwd pair, joined not replaced, each
   labelled by origin so the model can tell user scope from project scope.
   This alone would have answered call 1. Prompt-surface change: it moves
   request bytes every turn, so under BM-1 §3 it needs the request-byte
   gates and the paired bench.
2. **Say when there is no project.** When cwd has no VCS root, no
   workspace manifest, and no instruction file, state it — in the prompt to
   the model and in the banner to the human. A silent non-project workspace
   is the condition that made this expensive.
3. **Decide the dot-entry rule once, for both tools.** Either both show
   dot-entries or both hide them, with `.git`/`node_modules` skipped by
   name rather than by leading dot. Whichever way, document it in the tool
   descriptions so the model knows what it is not seeing.
4. **Fix the grep contradiction.** One line, zero risk, unrelated to this
   bug but adjacent to it and currently indefensible.
5. **De-scoped, tracked separately:** a `find_path` tool. Real gap, not
   this bug.

Remedy 1 is the fix. Remedies 2–4 are what stop the next silent fifteen
calls when remedy 1 does not apply.
