# DC-54 — `search_text` reads every file whole and synchronously, with no size cap and no binary check

- **id:** DC-54
- **class:** P1 — the product freezes solid, indefinitely
- **severity:** **P1.** One `readFileSync(file, "utf8")` on a large file
  owns the event loop for its whole duration. Nothing else runs: no
  frame, no liveness mark, no `esc`, no `ctrl+c` handler. On the owner's
  machine the call **never returned** — a watchdog killed it at 180s
  with the loop dead for the last 83 of them.
- **agent:** every version that has had `search_text`. Reproduced on the
  shipped **0.24.4**, i.e. this is NOT the defect DC-52 fixed.
- **status:** FIXED in 0.24.5, red before green. Ruled 2026-09-05: all
  five proposals accepted, plus the two sibling tools below.

## What the owner did

The owner typed a short request, in Chinese, asking kiso to take a
look at "reeled" (escaped for the CJK-free tree:
`\u5e2e\u6211\u67e5\u770b\u4e0b` + `reeled`). kiso was launched with the workspace at `~`. The model
read it as a name to look for, and issued two parallel calls
(`~/.kiso/sessions/2026-09-05T03-33-24-6394.jsonl`, seq 44–66):

```
search_text {"pattern":"reeled"}     <- no path, so root = workspace root = ~
list_dir    {}
```

`list_dir` returned in **4 ms** (seq 63 → 65). `search_text` reached
`tool_execution_started` at seq 60 and the log **ends there**. There is
no `tool_execution_succeeded`, no `tool_result`, no further record of
any kind. The session's pid (38806, from its `.lock`) is gone: the owner
killed the process.

The log ending mid-call is itself the evidence. The session writer runs
on the same event loop, so a blocked loop cannot append — the transcript
stops at exactly the instant the freeze begins.

## The measurement

The walk, as shipped, under `~` (depth cap 8, dotfiles and
`node_modules` skipped — stat only, no contents read):

```
dirs walked  83,450
files        296,924        <- each one readFileSync(…, "utf8")
bytes        1,063 GB       <- what search_text tries to turn into strings
elapsed      10.0s          <- traversal alone, without reading anything
```

47 of those files are over 50 MB. What each costs, measured:

| file | size | `readFileSync(…, "utf8")` |
|---|---|---|
| `…/aerials/videos/4C10….mov` | 467 MB | **succeeds** — 3,817 ms of dead loop, 2.06 GB RSS, split into 1,823,112 "lines" |
| `…/claudevm.bundle/rootfs.img` | 10.7 GB | throws `ERR_STRING_TOO_LONG` after 2,489 ms and 4.34 GB RSS — into a bare `catch {}`, silently |
| `…/com.docker.docker/…/Docker.raw` | 994 GB (sparse) | **never returns.** Still running when SIGKILLed at 90s |

## End-to-end, against the shipped 0.24.4 binary

Not a mirror of the code — the installed
`@vincemakes/kiso-tools-node@0.24.4`, its own `searchTextTool`, with a
5-second heartbeat on the event loop:

```
tool         search_text   root=/Users/vinve
  … event loop alive at 5s
  … event loop alive at 10s
  … event loop alive at 15s
  … event loop alive at 21s      <- already drifting: big reads starving it
  … (ticks continue, spacing 5→6s)
  … event loop alive at 97s
                                  <- NOTHING. 83 seconds of silence.
>>> 180.7s : STILL RUNNING — SIGKILLed
```

The drift from 5s to 6s spacing is the moderate files; the silence after
97s is one large one. Both are the same defect at different scales.

## Root cause

`packages/tools-node/src/index.ts`, `scanFile`:

```ts
const text = readFileSync(full, "utf8");
for (const [i, line] of text.split("\n").entries()) { … }
```

Three unbounded things in two lines:

1. **No size cap.** A 994 GB file is read as eagerly as a 40-line one.
2. **No binary check.** `.mov`, `.img`, `.raw`, `.a`, `.bin`, `weights.bin`
   are all "text" to this code.
3. **Synchronous.** R3 made the *walk* yield (`fs.promises.readdir`, plus
   a `setImmediate` every 64 files) and its comment claims this stops "a
   long read stretch" monopolising the loop. It does not, and cannot:
   `breathe()` runs **between** files. Nothing can preempt a single
   `readFileSync` once entered. The yield was built against the right
   diagnosis at the wrong granularity.

## Relation to DC-52

DC-52 is fixed and stays fixed: search no longer spawns `find` per
multi-link file, so the subprocess storm and the `find:` stderr written
over the composer are gone — the probe run above produced neither. DC-52
removed one cause of the freeze. This is the other one, which was never
in its scope. The owner's report of "it froze again" is accurate and is
not a regression of the DC-52 fix.

## The fix, as ruled

`search_text` — three bounds on the FILE and one on the CALL:

1. **Size, before anything is opened.** `st.size > 1 MiB` → skipped and
   counted. Not a prefix read: a partial match is a result that has to be
   explained, and a source file over 1 MiB is almost never what the model
   was looking for.
2. **Binary, from the head alone.** One `open`, an 8 KiB read at an
   explicit position (which by contract leaves the handle's own position
   at 0), a NUL check, and the same handle serves the read. `.mov`,
   `.img`, `.raw`, `weights.bin` stop being "text".
3. **The read is asynchronous**, and bounded above by ① at 1 MiB.
4. **A CALL budget: 20,000 files or 10 seconds, whichever trips first.**
   Per-file bounds are not enough — under `~` the walk still reaches
   296,924 files, and ten seconds of traversal with nothing on screen is
   the same freeze seen from the outside. The tool must ALWAYS return.
5. **One merged note, only when it happened:**
   `… N files skipped (large or binary) · stopped after M files — narrow the path`

`read_file` had the identical unbounded `readFileSync`, and the same
`Docker.raw` would have frozen it identically. It now **refuses** above a
64 MiB ceiling. Refuses rather than
truncates, and the reason is not conservatism: the `[rev:…]` token this
tool issues hashes the WHOLE file, so a revision computed over a prefix
could never equal the full-file hash `write_file` computes — every later
write to a large file would be refused as stale. A bounded read would
have bought a freeze-free read at the price of a write path that quietly
stopped working. No read, no revision, no lie.

`list_dir` was `readdirSync` (synchronous over the whole listing)
followed by a `.map` over EVERY entry, with the 200-entry slice only
after: a directory of 200,000 entries built 200,000 strings to show 200.
Now asynchronous, and truncated before it builds. Milder than the
`search_text` freeze and the same mistake — unbounded work before the
bound.

The bounds are `WorkspaceToolsOptions.limits`, defaulting to the ruled
constants. That surface exists because a gate that cannot set a budget
can only prove the default never fires.

### One deviation from the ruling, and why

The ruling said to make the reads asynchronous. `search_text`'s is.
`read_file`'s and `list_dir`'s are NOT, and this is deliberate.

The first build followed the ruling exactly, and
`apps/cli/tests/tui2-r1-visibility.test.ts` went red on this:

> THE DURABLE LOGS: the rolled session's events are the unrolled
> session's events — same types, same order, same contents.

Three concurrent `read_file` calls used to complete in issue order,
because a synchronous read completes inline. Made asynchronous, their
completion order becomes the libuv threadpool's to decide — so the
durable log of a session stopped being a function of the script and
started varying run to run. The failing comparison was `r0, r1, r2`
against `r0, r2, r1`. That test proves the exploration rollup is
display-side only by comparing a PTY session's log to a pipe session's,
and it cannot do that job over a log that varies. Replay determinism is
downstream of the same property.

The reasoning that settles it: **the freeze came from UNBOUNDED work,
not from synchronous work.** Once the ceiling is in place the worst case
`read_file` can reach is a 64 MiB read — about 100 ms, measured —
against the 180+ seconds this finding is named for. `list_dir` is one
`readdirSync` whose cost is the directory's size, which no bound of ours
can shrink and which async would not shrink either. Neither buys enough
to be worth a nondeterministic log.

`search_text` keeps its async read: it is bounded at 1 MiB by ① anyway,
and its cross-call completion order was never deterministic — the walk
has been asynchronous since R3, and its duration varies with the tree.

Verified: `tui2-r1-visibility` green three runs in a row after the
revert.

Open question resolved by the ruling: **no refusal by root size.** A
workspace rooted at `~` is DC-49's question and belongs to the owner; the
tool layer's duty is to return within budget under any root, and to say
what it did not look at.

## What this says about the gate

The DC-52 round added a PTY gate proving `find` no longer writes to the
terminal. It passed, and it was a real gate — but it was scoped to the
subprocess, and "the search returns at all" was never asserted. A gate
that watches one cause of a freeze cannot see the other. The gate this
needs: a fixture tree containing one oversized file and one binary file,
and an assertion that `search_text` over it **returns**, within a
budget, with the loop still turning.

### Building that gate took three tries, and the first two were green

Recorded because the failure mode is the finding's own lesson, one level
down — a gate can be scoped to the wrong thing just as R3's was.

**Draft 1 — a 32 MiB file, 120 ms threshold.** Green against the broken
code. `readFileSync` of 32 MiB is 36 ms on this machine; even 256 MiB is
163 ms. I had guessed "hundreds of milliseconds" and never measured.

**Draft 2 — a 2 GiB SPARSE file**, instant to create and the exact shape
of the `Docker.raw` that froze the owner's machine. Green, for a worse
reason: 2 GiB is past V8's maximum string length, so the broken code
threw `ERR_STRING_TOO_LONG` into its bare `catch {}` and the file never
appeared in the output. Both the skip case AND the liveness case were
satisfied *by the defect*. The fixture the defect survives is not a
fixture.

**Draft 3 — 128 MiB of real text** (measured: 200/328/200 ms of stall
across three trials, 39 ms to write), needle on line 1 so an unfixed
search REPORTS the file. Eight cases red.

And the instrument itself was wrong once: `longestLoopStall` cleared its
`setInterval` as soon as the awaited call resolved. An awaited chain
resolves through MICROtasks, which run before timers — so the interval
never fired to record the 300 ms it had just sat through, and both
liveness cases stayed green over measured blockage. The final gap has to
be taken explicitly at the end, not left to the timer.

One more, found while writing the fix rather than by a test: the call
budget used `stoppedAt > 0` as its "did we stop" sentinel, so a
wall-clock budget expiring BEFORE the first file read as "never
stopped" — the walk ended in silence, the one outcome every note in this
function exists to prevent. The case that catches it uses
`searchMaxMs: -1`, already expired at setup, because the case written
with `searchMaxMs: 1` passed only on the luck of a few files fitting
inside one millisecond.

### What is NOT gated, and why

`list_dir`'s defect is real but mild, and no fixture this suite can
afford discriminates it: 2,000 entries cost 1 ms unfixed. Showing it
needs ~200,000 entries, which costs more to create than the defect costs
to suffer. So the `list_dir` cases gate the CONTRACT the fix must not
break, and there is deliberately no loop-liveness case there — it would
be green against the defect, which is worse than no case at all.
