# DC-30 — the expand ring was keyed on our own printed bytes

Status: FIXED in R4a (2026-08-30).
Class: hidden coupling — an affordance that was load-bearing.
Surface: `packages/tui/src/compositor.ts`, the commit path.

## The defect

A cell joined the expand ring only if the rows it had just rendered
contained the literal string `ctrl+r`:

```js
if ((cell.kind === "tool" || this.#segmentOf(i)?.headCell === i) && lines.some((l) => l.includes("ctrl+r"))) this.#collapsed.unshift(i);
```

So the printed affordance was not a hint about the feature — it WAS the
feature's enabling condition. Retiring the printed key (the owner's R4a
ruling) would have silently emptied the ring and taken `ctrl+r` with it:
not a missing label, a missing capability, with every existing gate
still green because they all asserted the label.

Found only because the ruling forced the question. The comment above the
line even described the mechanism approvingly — "the detection is the
renderer's OWN output" — without noticing that this makes a cosmetic
decision structural.

## The fix

The ring captures by IDENTITY: a fold head is a fold head because its
segment says so (`#segmentOf(i)?.headCell === i`), and a tool cell is
expandable when it is hiding rows. Nothing depends on what the row says.

## The class, for the next reader

**An affordance must never be the enabling condition for the thing it
advertises.** When it is, the label cannot be changed without changing
behaviour, and no gate that asserts the label can tell you so — the
label and the capability are the same fact, and the tests can only see
one of them.

The same shape is worth grepping for wherever a renderer's output is
fed back into a decision.
