# REL-0152-D9 — a paste cost time in the square of its size

- **id:** REL-0152-D9
- **class:** performance / input
- **severity:** P2 — a routine gesture freezes the composer
- **agent:** kiso 0.15.4
- **found by:** owner dogfood, 2026-08-25 — the capsule appears, but
  only after a long wait
- **status:** FIXED

## The measurement

Every pasted character went through `#insert`, which splices one code
point and then reflows — and a reflow finds the cursor's line bounds and
measures its width, which is linear in the line. On the shipped build:

| paste | before | after |
|---|---|---|
| 1k | 4.3 ms | 1.4 ms |
| 10k | 33.5 ms | 1.1 ms |
| 30k | 277.6 ms | 1.5 ms |
| 100k | ~3 s (extrapolated) | 1.2 ms |
| 400k | ~40 s (extrapolated) | 6.2 ms |

Tripling the input multiplied the time by eight, which is the signature.

## The fix

The run is collected in `#pasteRun` while the paste is in flight and
spliced in ONCE when it closes: one splice, one reflow, and the line
arithmetic done on a finished string instead of re-done at every
character of it. It survives chunking by construction — a terminal
delivers a large paste in many reads, and this is a field, not a local.

`String.fromCodePoint(...run)` is NOT used: the argument list is the
stack, and a big paste would throw RangeError. The conversion is chunked.

## The visible consequence

Mid-paste the composer is empty; the text appears when the paste
completes. That is a declared supersession of one assertion in
`editor-multiline.test.ts` (the CR|LF-split case peeked at the buffer
between chunks). The property that case exists for — every boundary
yields exactly one 0x0A, including a pair split across stdin reads — is
untouched and still asserted.

## Evidence

`packages/tui/tests/paste-capsule.test.ts`: a 3000-line paste delivered
in 997-byte chunks arrives as one paste in order; a 400k paste stays
under a frame; the capsule's line count is the text's.
