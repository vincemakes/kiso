# REL-0152-D1 — a streaming frame repaints the whole screen, and a
# terminal without DEC 2026 shows it half-done

- **id:** REL-0152-D1
- **class:** renderer / frame atomicity
- **severity:** P1 — **usability, not cosmetics.** Raised 2026-08-25 on
  durable-log evidence: the defect makes typed input invisible and drops
  complete model answers off the screen. The first assessment called a
  tear "self-healing on the next frame"; that is true of the tear and
  false of what rides on it.
- **agent:** kiso 0.15.2 and every earlier version
- **found by:** owner dogfood on Terminal.app, 2026-08-25
- **status:** CLOSED — NOT OURS. Terminal.app's Marks feature.
  Gates landed as `it.fails` in `packages/tui/tests/apple-terminal-frames.test.ts`.

## The behaviour

Stray `[` and `]` at row edges during streaming, and the input box's
layout tearing while text arrives.

## What it actually costs — three facts from one session's durable log

Owner dogfood, session `2026-08-25T07-29-29-32d9`, 6,581 events. The log
is the truth; the screen was not.

**1. A typed message looked swallowed. It was not.**
The owner typed a six-character question asking why it had stopped,
and saw nothing appear. It is in the log at
`seq 4386`, complete. The input reached the runtime and the RENDERER lost
it. No data was lost — but a user who cannot see what they typed has no
way to know that.

**2. The session looked stopped. It was not.**
It ran to `stop reason=end_turn` at `seq 6579` and `terminal` at 6580 —
a clean, complete turn.

**3. A 1,478-character answer never reached the screen.**
The turn's reply opens by saying it had not stopped and had finished
reading, and ends by asking which task to take next.
The owner never saw a word of it, and reasonably concluded the agent had
hung.

So the failure mode is not "the screen looks briefly wrong". It is
**input you cannot see and output you never get**, on a product whose
promise is that you can hand it work and trust the return state.

## The owner's own clue, and what it confirms

> resizing the window makes the brackets disappear

`onResize` writes `\x1b[0J` and sets `#fullRedraw`, so the next frame
repaints everything. The brackets vanishing under that is the proof that
they are **residue of a frame that was written half-way** — not
characters anything intended to draw. One full repaint erases them.

Brackets, the swallowed input and the lost answer are one root cause with
three faces, and which face appears depends only on where the terminal
happened to paint between two of our writes.

## What it is NOT

REL-0150-D1 attributed this to Apple Terminal lacking DEC 2026 and shipped
a conservative mode keyed on `TERM_PROGRAM`. **That detection works.**
Measured on the published 0.15.2 artifact:

| TERM_PROGRAM | `?2026h` | `?25l` |
|---|---:|---:|
| `Apple_Terminal` | 0 | 3 |
| `iTerm.app` | 3 | 0 |

An earlier pass of this investigation concluded the conservative path was
dead code. **That was wrong, and it came from a broken measurement** — a
Python heredoc counting `b'\\x1b'`, which is a literal backslash, not the
ESC byte, so every count was 0. Recorded because a wrong measurement
produced a confident wrong diagnosis for the third time this round.

## The real cause, measured

`?25l/?25h` hides the cursor. **It is not a frame transaction.** Between
those two bytes the renderer still erases and rewrites row after row, and
a terminal without DEC 2026 is free to paint after any one of them.

Real PTY, 120 deltas, 40x120:

| | |
|---|---:|
| frames (the 40ms coalesce is working) | 3 |
| bytes per frame, median | 1,758 |
| **erased rows per frame, median** | **45** |
| erased rows per frame, max | 55 |

**45 rows erased in a 40-row terminal — the whole screen and then some,
per frame.** Not too many frames; frames that are too big. That is why
widening the coalesce window (16→40ms) did not fix it: it reduces frame
COUNT, and the defect is frame SIZE.

Composition of the 45: ~31 are gap erase-lines (blanking rows that are
already blank), the rest are the status row, box, composer, queue and
menu — none of which change between two streaming deltas.

## The fix that was built and reverted

A row-level diff: remember each screen row's last content, skip rows
whose content is unchanged. It worked on the target metric — 40 erased
rows to 8, gates green — and then failed the A7 replay at 40x12 frame 47
with **status-row text where the box top belongs**.

Row-keyed caching is correct only if every path that changes what a row
NUMBER means invalidates it. Four were found and handled (scroll, commit,
resize, the `0J` erase in `onResize`). The A7 replay proved there is at
least one more. This file's own history — A7, A8, A8b, TUI2-MD-1, the
W11 boundary pileup — is a list of such paths that is still growing.

**Trading a tear that self-heals on the next frame for a mislaid box that
does not is a bad trade**, so it was reverted rather than pursued.

A separate self-inflicted lesson from the same attempt: routing
`#drawFull`'s writes through the diffing writer made it skip rows and
emit near-empty frames — 44 test failures that looked like the diff
design failing and were not. `#drawFull`'s contract is "every row is
painted"; it may RECORD what it wrote, never consult.

## The shape the fix should take

Claude Code's, in `src/ink/` — vendored Ink rewritten around a screen
buffer:

```
React tree → Screen (cell buffer, CharPool/StylePool interned)
           → screen.diff (cell by cell, over the region that could change)
           → Patch[] (cursorTo / cursorMove / styleStr / stdout)
           → only the changed cells are written
```

It uses **no DEC 2026 at all** — grep finds zero. It does not need frame
synchronisation because it does not repaint what did not change. Its
correctness comes from HOLDING a copy of the screen, not from remembering
what was written, which is the difference that makes the open set of
invalidation paths stop mattering.

pi takes the same idea at row granularity (first/last changed line).

This is an architecture round, not a patch.

## Acceptance, when it is attempted

- the two `it.fails` gates flip to `it` in the same commit;
- the A7 replay and the full compositor suite stay green — 729 tests, the
  geometry cases are the ones that caught the reverted attempt;
- **and the owner streams on Terminal.app.** A PTY proves byte counts and
  a layout model; it cannot prove a terminal never shows a half-frame.
  Sixty-three D1 tests were green while the owner watched it tear, because
  every one of them asserted that control sequences were present and
  paired, and none asserted how much the frame between them wrote.


## 2026-08-25 — what the instrument ruled out

The owner's newest observation is the sharpest one yet: the brackets
appear when new content is SENT and go away when the session pauses. So
they belong to frames, not to the settled screen.

With `KISO_TRACE_BYTES` (REL-0152-D12) the byte-stream half of the
question is now answered, and the answer is negative in a useful way.
235 real frames — the A7 fixture session replayed through the real
compositor at 140x30 with `TERM_PROGRAM=Apple_Terminal`, so the
conservative frame mode is the one under test:

- **0** `[` starting a row that is not a known bracketed message;
- **0** bare ESC with no sequence following it;
- **0** writes that END mid-escape.

Every escape leaves kiso whole, in one write. Nothing in that stream can
become a stray `[` on the way out.

Two candidate mechanisms were named and eliminated:

1. **A bracketed row whose interior was overwritten.** The symptom's
   shape — `[` in column 1, content, a gap, `]` in the last column — is
   exactly what a wide bracketed row looks like after something paints
   into the middle of it. `renderStatusLine` does emit that shape
   (`[turn N · in … · cache … · ctx ~X%]`), which made it the obvious
   suspect. It has NO caller in the CLI: it is exported from the tui
   index and nothing invokes it. The recap row that the screenshot's
   content resembles (`▞ 2s · 0 tools · in … · cache … · ctx left ~…%`)
   is not bracketed at all.
2. **A frame painting a row's middle without erasing its ends.** Every
   CUP-with-content write in the compositor carries `\x1b[0K`; the only
   CUP writes without it are cursor moves that write no text. Within a
   frame, a painted row is erased first and its old tail cannot survive.

So: the bytes are clean, and the two ways kiso itself could produce the
shape are ruled out. What is NOT ruled out, and cannot be from here, is
the terminal side — including the one mechanism this analysis cannot
see, which is the OS splitting a single large `write()` into several
reads. REL-0152-D13 measured a 3000-line paste emitting 260,298 bytes in
ONE frame; a write that size is split by the kernel, and a terminal
whose escape parser gives up at a chunk boundary prints the remainder,
where an abandoned CSI leaves exactly `[`.

The next observation is the owner's own capture, in Terminal.app, with
their content and their width. Everything above is what could be
established without it, so that the capture is read against a short list
rather than an open field.


## 2026-08-26 — the brackets are NOT ours, proven on the owner's own text

0.15.6 shipped REL-0152-D14 (autowrap off for the frame). The owner's
verdict separates this finding cleanly in two:

- **the layout during streaming is FIXED** — the owner reports the
  composer box is no longer wrecked while a turn streams;
- **the brackets are unchanged.**

So they are two defects that shared a symptom, and the second one is
now settled. Their exact answer text was rendered through the real
compositor at their width, in conservative mode, and the frame measured:

```
literal [ outside a CSI : 0
literal ] outside a CSI : 0
frame writes            : 1  (776 bytes)
the continuation row    : ESC[5;1H  ESC[0K  <the wrapped tail of the answer>
```

kiso emits no bracket, in one unsplit write, and positions the row that
carries them with a plain CUP and erase. Combined with the owner's own
capture (0 unexplained edge brackets, 0 bare ESC, 0 split writes) and
the clean screen a correct terminal model produces from those bytes,
the character is made on the terminal side. Nothing kiso can change
about the CONTENT of its frames removes it.

What remains OURS in this finding is the other half, and it is
unaffected by any of that: a streaming frame still erases and rewrites
rows that did not change — 13 row erases per keystroke, measured, for a
change that touches one row. That is the cell-diff work, and it shares
its round with REL-0152-D7.

### The next observation, for the terminal half

Two cheap discriminators, both on the owner's side, chosen because they
separate the remaining explanations rather than adding detail to one:

1. **Select the row and copy it.** If the brackets come along, they are
   characters in the terminal's grid and something put them there. If
   they do not, they are drawn decoration — a Terminal.app feature or
   setting, not text at all.
2. **Run once with `LANG=en_US.UTF-8`.** The capture shows
   `LANG=zh_CN.UTF-8`; if the brackets vanish without it, the CJK locale
   path in the terminal is where they are made.


## 2026-08-26 — CLOSED. It was never text.

The owner selected the affected rows and copied them. **The brackets did
not come along.** The pasted text is clean end to end — the session
line, the banner, the version, the extension list, the resume rows — and
carries no bracket anywhere.

So they are not characters in the terminal's grid, and nothing kiso
writes could have put them there, because kiso writes characters.

Terminal.app 470 has exactly this feature. Its menu carries:

```
Marks
  Show Marks
  Automatically Mark Prompt Lines
  Clear to Previous Mark
```

It marks the lines it believes are shell prompts and DRAWS the marks as
brackets. Every observation follows:

| observation | explanation |
|---|---|
| they do not copy | a mark is decoration, not a cell |
| the last pair brackets the SHELL prompt, after kiso exited | that is a prompt |
| they bracket kiso's composer row | `› ` matches the heuristic |
| they appear after a message is sent | a new prompt-looking row appears |
| a resize clears them | marks re-evaluate |
| ctrl+C then relaunch makes TWO | one marked prompt per launch |
| the reference implementation is immune | its composer does not match, or it is on the alternate screen where marks do not apply |

The owner turns it off in Terminal.app: Edit → Marks → uncheck
"Automatically Mark Prompt Lines".

## What this cost, and why

Three rounds earlier, THIS FILE proposed the experiment that settles it:

> Select the row and copy it. If the brackets come along, they are
> characters in the terminal's grid and something put them there. If they
> do not, they are drawn decoration — a Terminal.app feature or setting,
> not text at all.

I wrote the right experiment and then did not run it. I built three more
instruments instead — the byte trace, then stderr capture, then querying
the terminal for its own geometry. Each was well made and each answered
the same question I had already answered in round one: what does kiso
send? Clean.

The question nobody asked for three rounds was whether these characters
were characters at all — a five-second action, written down and left as
prose.

Two real defects were found on the way and both stand on their own
merits: REL-0152-D17 (stderr was a second writer the held-screen
renderer did not know about, and the trace could not see it) and
REL-0152-D19 (the dock reset the terminal on exit and never on entry,
which D14 had made worse). Neither is the cause of this finding, and
D19's release note called itself a hypothesis for it. That hypothesis is
**refuted**.

The lesson is not "ask the user sooner". It is that a discriminating
experiment I have already written down IS the next action — not
background material to be filed while I go on doing the thing I am
better at.
