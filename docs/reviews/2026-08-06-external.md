---

    一句话概括：
    > **Kiso 是一个面向 TypeScript 开发者的、以事件溯源和崩溃恢复为核心的 Coding Agent 框架。**
    它解决的不是“AI 能做多少事情”，而是一个更底层的问题：
    > Agent 调用模型、修改文件、运行命令、等待人工审批的过程中，如果进程突然被杀死，怎样恢复到正确状态，既不丢任务，也不重复执行危险操作？
    ---
    ## Kiso 实际在做什么
    Kiso 的核心执行模型是：
    ```text
    用户输入
    → 模型流式输出
    → 生成工具调用
    → 权限判断
    → 记录执行开始
    → 执行工具
    → 记录执行结果
    → 继续模型循环
    → 写入明确的终止事件
    ```
    这些步骤不是只保存在内存里，而是全部变成带有连续 `seq` 的事件，追加到 JSONL 文件中。
    所以一次 Agent 运行不是一个黑盒函数，而是一条可以重放的轨迹：
    ```text
    seq 0: user_input
    seq 1: text_start
    seq 2: tool_call_end
    seq 3: permission_requested
    seq 4: permission_decided
    seq 5: tool_execution_started
    seq 6: tool_execution_succeeded
    seq 7: tool_result
    seq 8: terminal
    ```
    模型上下文、CLI 显示、会话恢复、评测和审计都从同一条事件流投影出来，而不是各自维护一份状态。
    这就是 Kiso 最核心的设计：
    > **事件日志才是真相，内存状态只是日志的暂时投影。**
    ---
    ## 它和前两个项目完全不是一个层级
    | 项目      | 本质            | 核心问题                  |
    | ------- | ------------- | --------------------- |
    | Pinvou  | 桌面 AI 工作台     | 怎样把聊天、办公、设计、代码放进一个产品  |
    | LingTai | 长期驻留 Agent 系统 | Agent 如何跨数周积累知识、技能和身份 |
    | Kiso    | Agent 执行框架    | Agent 如何可靠执行、审计、暂停和恢复 |
    Kiso 没有试图自己解决知识库、视觉设计、微信机器人、数字人格、长期科研等所有问题。
    它主要提供：
    * Agent Loop
    * Provider Adapter
    * Tool Registry
    * Hook
    * 权限和人工审批
    * 事件日志
    * 会话持久化
    * 崩溃恢复
    * 上下文压缩
    * CLI 参考实现
    * MCP、Skills、Subagent 扩展
    所以理论上，**Pinvou 或 LingTai 这样的产品都可以构建在 Kiso 这种执行内核之上**。
    ---
    ## 架构非常清楚
    Kiso 把系统分成两层。
    ### 1. 小型 Core
    `@vincemakes/kiso-core` 只负责：
    ```text
    协议
    事件类型
    Agent Loop
    Tool Contract
    Hooks
    Modes
    Permissions
    Compaction
    Terminal Outcome
    ```
    Core 被强制限制在 2,000 行以内，当前 README 展示的统计已经接近这个上限。
    ### 2. 外围 Packages
    真正面向产品的能力放在独立包中：
    ```text
    @vincemakes/kiso-runtime
    @vincemakes/kiso-provider-anthropic
    @vincemakes/kiso-provider-openai
    @vincemakes/kiso-tools-node
    @vincemakes/kiso-tui
    @vincemakes/kiso-code
    @vincemakes/kiso-evals
    ```
    另外还有 MCP、Skills 和 Subagent 扩展。根仓库本身就是一个 npm workspace，各包分别构建、测试和发布。
    这个边界比 Pinvou 清楚很多：
    ```text
    Core 不知道 CLI
    Core 不知道 Anthropic SDK
    Core 不知道文件系统会话
    Core 不知道 MCP
    Core 不知道产品界面
    ```
    而 Runtime 只依赖 Core，Provider 又作为可选包接入。
    ---
    ## 最大亮点：真正认真处理了崩溃窗口
    很多 Agent 框架的工具调用逻辑大概是：
    ```ts
    const result = await tool.execute(args);
    history.push(result);
    ```
    问题是，如果进程在工具已经执行、结果还没写入 history 时崩溃，就不知道工具究竟有没有执行成功。
    例如：
    ```text
    Agent 调用了“向客户转账”
    → 银行接口已经成功
    → 进程崩溃
    → Agent 重启
    → 日志里没有成功结果
    → 再执行一次
    ```
    Kiso 会在执行之前先持久化：
    ```text
    tool_execution_started
    ```
    执行成功后再写：
    ```text
    tool_execution_succeeded
    ```
    如果重启时只看到了 `started`，没有看到成功或失败结果，它就把执行标记成：
    ```text
    uncertain
    ```
    然后要求人类选择：
    ```text
    rerun
    或
    abandon
    ```
    因此它不会假装自己知道工具有没有成功，也不会擅自重试。事件协议中明确区分了执行开始、成功、失败、人工裁决以及不确定状态。
    ---
    ## `kill -9` 不是一句营销口号
    项目真的写了一个端到端测试：
    1. 在真实 PTY 中启动 Kiso；
    2. 第一次修改文件成功；
    3. 第二个 Shell 命令运行到一半；
    4. 对整个进程组执行真实 `SIGKILL`；
    5. 检查磁盘事件流没有损坏；
    6. 确认只有一个执行处于 uncertain；
    7. 启动一个全新的进程执行 `kiso resume`；
    8. 注入人工 `rerun` 裁决；
    9. 原来的执行轨迹继续运行，而不是从头重放；
    10. 第三个文件修改完成，并写入 Terminal 事件。
    这一点比大部分号称“Durable Agent”的项目扎实。
    它不是简单地把聊天记录保存下来，而是验证了：
    > **执行中的 Agent 被硬杀以后，新的进程能沿着原轨迹继续。**
    ---
    ## Session Store 也不是简单写 JSON
    它的 Session Store 做了不少数据库级别的工作：
    * Append-only JSONL
    * 每个事件写入后 `fsync`
    * 单 Session 单写者锁
    * 检测并修复未写完整的尾行
    * 检查事件序号是否连续
    * 用 CAS 防止旧 Session Handle 继续写入
    * 一旦磁盘写入失败，当前内存 Session 会被标记为 poisoned，禁止继续工作
    每次事件都是**先落盘，再向上层 yield**。这意味着用户界面看到一个事件时，它原则上已经持久化。
    `AgentSession` 同样明确规定：
    ```text
    1. 用户输入先持久化
    2. Kernel 执行
    3. 每个事件先持久化
    4. 然后才交给消费者
    ```
    审批决定、不确定执行裁决和上下文摘要也都属于持久状态。
    ---
    ## 它的 API 也比较像一个框架
    使用方式是：
    ```ts
    const agent = createAgent({
      model: "claude-sonnet-5",
      tools,
      store,
      adapter,
    });
    const session = await agent.session({ id: "demo" });
    for await (const event of session.run("检查这个项目")) {
      // 消费事件
    }
    ```
    高层 Runtime 只负责把：
    ```text
    模型
    工具
    Provider
    Session Store
    权限策略
    Hooks
    Extensions
    ```
    组合在一起。
    这比 LingTai 那套 Soul、Molt、Avatar、Karma 更容易让普通 TypeScript 开发者理解。

    # 这个项目最强的地方
    ## 1. 北极星非常清楚
    它只强调：
    > **Reliable Agent Execution**
    不是桌面 AI 操作系统，也不是数字生命。
    这让 README 中每项能力基本都能回到同一件事：
    * 事件流是为了恢复；
    * Approval 是为了恢复；
    * Tool Receipt 是为了恢复；
    * Terminal 是为了诚实结束；
    * Compaction 也必须可重放；
    * Extension 也不能破坏日志语义。
    产品逻辑是闭合的。
    ## 2. 对失败语义很敏感
    它不会把所有失败都压缩成 `error: true`。
    例如明确区分：
    * 输入参数错误
    * 前置条件不满足
    * 暂时性错误
    * 致命错误
    * 模型拒绝
    * 内容过滤
    * 上下文超限
    * 人工中止
    * 达到最大回合数
    很多框架在正常路径上很好看，一遇到失败就全部变成字符串。Kiso 的设计重点恰恰在失败路径。
    ## 3. Extension 边界合理
    MCP 被实现成独立扩展，而不是侵入 Kernel：
    > MCP Server 被转换成工具，Kernel 无须知道 MCP 的存在。
    这是对的。
    Agent Framework 最容易犯的错误，就是所有能力最终都进入一个巨大的 `AgentSession` 类。Kiso 明确规定，Packages 通过事件流和 Hooks 通信，不允许出现第二个中央 Hub。

    # 但我也看到几个真实风险
    ## 1. “Exactly-once tool execution”说得稍微过头了
    严格来说，Kiso 并不能保证所有外部副作用 exactly once。
    例如进程在这里崩溃：
    ```text
    银行已经完成转账
    但 tool_execution_succeeded 还没有落盘
    ```
    Kiso 仍然不知道转账是否成功，所以只能标记为 uncertain，让人选择 rerun 或 abandon。
    因此更准确的表述是：
    > **Crash-consistent tool execution with durable receipts and explicit uncertainty resolution.**
    或者中文：
    > **具备持久执行凭证和不确定状态裁决的崩溃一致性工具执行。**
    它解决得已经非常好了，但不是分布式系统意义上的通用 exactly-once。
    真正的 exactly-once 仍然需要工具本身支持：
    * 幂等键
    * 事务 ID
    * 状态查询
    * 去重机制
    我建议不要把 “exactly-once” 当成最主要的对外承诺，否则懂分布式系统的人容易第一时间挑战它。
    ---
    ## 2. 2,000 行限制可能从纪律变成宗教
    限制 Core 大小是好事，但硬性规定：
    > 超过 2,000 行的 PR 一律关闭
    容易导致几种副作用：
    * 为了省行数，把逻辑写得过密；
    * 把复杂度转移进庞大的类型协议；
    * 把本应属于 Core 的语义推到 Runtime；
    * 大量注释不计行数，实际认知复杂度并没有下降；
    * Package 数量越来越多，系统总体复杂度照样增长。
    事实上，Kiso 的 `events.ts` 已经承载了非常多持久协议语义，Core 虽小，但协议面并不小。
    更好的纪律可能是：
    > Core 必须保持可解释、无产品逻辑，并设置软上限；突破时必须提交 ADR。
    而不是把 2,000 当成永远不可改变的物理定律。
    ---
    ## 3. “小 Core”不等于“小框架”
    Core 可以只有两千行，但完整系统仍然包含：
    ```text
    Core
    Runtime
    Providers
    Node Tools
    TUI
    CLI
    Evals
    MCP
    Skills
    Subagents
    Config
    Trust
    Compaction
    ```
    所以对外最好说：
    > **Small kernel, growable framework**
    而不是让用户误以为整个框架只有两千行。
    README 当前其实已经逐步在澄清这一点，但前面的“2,000-line core”仍然非常抢眼。
    ---
    ## 4. Session Lock 对环境有额外要求
    当前 Session Store 为了获得 `flock`，会启动一个 `python3` Helper 进程来持有文件锁。
    这对于一个 Node/TypeScript 框架来说有点奇怪：
    ```text
    使用 Kiso Runtime
    → 机器还必须有 python3
    → 依赖 Python 提供 flock helper
    ```
    它会带来：
    * Windows 兼容问题；
    * 精简容器内没有 Python；
    * Node 用户不理解为什么启动了 Python 子进程；
    * 锁 Helper 崩溃后的额外状态；
    * 打包成单文件 CLI 更麻烦。
    这应该算当前最明显的工程债。
    长期更适合：
    * 使用原生 Node 文件锁库；
    * 做一个很小的 Rust/N-API Sidecar；
    * 或根据平台分别实现锁；
    * 允许注入 Store Lock Adapter。
    ---
    ## 5. Durable Event Schema 会成为长期负担
    Kiso 的所有优势都建立在事件日志上，同时这也是它未来最大的维护成本。
    一旦用户磁盘里已经存在：
    ```text
    0.1.5 的事件
    0.1.20 的事件
    1.0 的事件
    ```
    后续版本必须永远正确重放这些历史事件。
    这意味着：
    * 事件不能随便删；
    * 字段不能随便改；
    * Projection 必须向后兼容；
    * Compaction 算法变化不能改变旧日志结果；
    * Provider 行为变化不能破坏历史；
    * Extension 也不能写入不可恢复状态。
    项目已经在旧 `compacted` 事件兼容、可选字段和版本语义上处理这些问题，说明作者意识到了风险。
    但在 0.1 阶段就拥有这么大的 Durable Event Union，未来演进会比较辛苦。
    ---
    ## 6. 目前还是非常早期
    当前发布版本是 `0.1.23`，API 和事件协议仍在快速演进。
    所以它目前更适合：
    * 框架作者；
    * Agent 基础设施开发者；
    * 需要审计和恢复的内部 Agent；
    * 愿意参与早期设计的人。
    还不适合承诺：
    > 装上以后马上获得一个成熟、完整、跨平台的 Claude Code 替代品。

    # 和 Pinvou、LingTai 放在一起评价
    ### 产品清晰度
    ```text
    Kiso > LingTai > Pinvou
    ```
    Kiso 的每个功能都围绕可靠执行。
    LingTai 围绕长期 Agent，但世界观和术语很多。
    Pinvou 横向功能太多，主线最模糊。
    ### 架构克制
    ```text
    Kiso > LingTai > Pinvou
    ```
    Kiso 明确区分 Kernel、Runtime、Provider、Tool、Surface 和 Extension。
    LingTai 的 TUI/Portal/Kernel 边界也不错，但整个系统规模非常大。
    Pinvou 最像一个不断增加功能的桌面产品。
    ### 长期自治能力
    ```text
    LingTai > Kiso > Pinvou
    ```
    LingTai 专门处理长期目标、知识、角色和子 Agent。
    Kiso 主要保证执行轨迹可靠，并不直接提供长期人格和知识成长体系。
    ### 作为开源 Agent Framework
    ```text
    Kiso > LingTai > Pinvou
    ```
    这个维度，Kiso 是三个里面最合适的。
    ---
    # 我的最终判断
    **这是三个项目里我最认可的一个。**
    它没有追求“AI 万能工作台”，也没有建立过重的数字生命叙事，而是找到了 Agent 工程中一个真正困难且普遍存在的问题：
    > **如何让 Agent 的执行过程可恢复、可审计、可裁决，并在崩溃后继续。**
    它目前的价值不是“功能比 Claude Code 多”，而是：
    > **提供一个可以用来构建 Claude Code 类产品的可靠 TypeScript 底座。**
    我会把它定位成：
    > **Kiso is a durable TypeScript agent framework for building coding agents that can pause, crash, resume, and remain correct.**
    中文就是：
    > **Kiso 是一个面向可靠执行的 TypeScript Agent 框架，让 Coding Agent 即使暂停、崩溃或重启，也能从正确状态继续工作。**
    核心方向没有问题，而且明显比 Pinvou 更克制、更像基础设施。现在最重要的不是继续加很多功能，而是守住三件事：
    1. 把“崩溃一致性”做成无可争议的行业标杆；
    2. 降低 README 和事件协议的理解门槛；
    3. 解决 Python `flock` Helper 和跨平台 Runtime 这类基础工程问题。
    **Pinvou 是功能集合，LingTai 是 Agent 世界观，Kiso 才是 Agent 工程内核。**
