below; the review text is archived VERBATIM.

---

    In one sentence:
    > **Kiso is a coding-agent framework for TypeScript developers, built on event sourcing and crash recovery.**
    What it solves is not "how much AI can do" but a more fundamental question:
    > When the process is suddenly killed while the agent calls a model, edits files, runs commands, and waits for human approval — how do we recover to the correct state, losing no tasks and re-running no dangerous operation?
    ---
    ## What Kiso actually does
    Kiso's core execution model is:
    ```text
    user input
    → model streaming output
    → a tool call is generated
    → permission check
    → execution start is recorded
    → the tool executes
    → the execution result is recorded
    → the model loop continues
    → an explicit terminal event is written
    ```
    These steps are not kept only in memory — they all become events with contiguous seq numbers, appended to a JSONL file.
    So an agent run is not a black-box function but a replayable trajectory:
    ```text
    seq 0: user_input
    seq 1: text_start
    seq 2: tool_call_end
    seq 3: permission_requested
    seq 4: permission_decided
    seq 5: tool_execution_started
    seq 6: tool_execution_succeeded
    seq 7: tool_result
    seq 8: terminal
    ```
    The model context, CLI display, session recovery, evaluation, and audit are all projected from the same event stream, rather than each maintaining its own state.
    That is Kiso's most central design:
    > **The event log is the truth; in-memory state is only a temporary projection of the log.**
    ---
    ## It is not on the same level as the previous two projects
    | Project  | Essence        | Core question                  |
    | ------- | ------------- | --------------------- |
    | Pinvou  | desktop AI workbench     | how to put chat, office, design, and code into one product  |
    | LingTai | long-resident agent system | how an agent accumulates knowledge, skills, and identity over weeks |
    | Kiso    | agent execution framework    | how an agent executes, audits, pauses, and recovers reliably |
    Kiso does not try to solve everything itself — knowledge bases, visual design, WeChat bots, digital personas, long-term research, and so on.
    It mainly provides:
    * Agent Loop
    * Provider Adapter
    * Tool Registry
    * Hook
    * Permissions and human approval
    * Event log
    * Session persistence
    * Crash recovery
    * Context compaction
    * CLI reference implementation
    * MCP, Skills, and Subagent extensions
    So in theory, **products like Pinvou or LingTai could be built on an execution kernel like Kiso's**.
    ---
    ## The architecture is very clear
    Kiso divides the system into two layers.
    ### 1. A small Core
    @vincemakes/kiso-core is only responsible for:
    ```text
    Protocol
    Event types
    Agent Loop
    Tool Contract
    Hooks
    Modes
    Permissions
    Compaction
    Terminal Outcome
    ```
    The core is hard-capped at 2,000 lines, and the statistics shown in the current README are already close to that limit.
    ### 2. Peripheral packages
    The capabilities that truly face the product live in separate packages:
    ```text
    @vincemakes/kiso-runtime
    @vincemakes/kiso-provider-anthropic
    @vincemakes/kiso-provider-openai
    @vincemakes/kiso-tools-node
    @vincemakes/kiso-tui
    @vincemakes/kiso-code
    @vincemakes/kiso-evals
    ```
    There are also MCP, Skills, and Subagent extensions. The root repository itself is an npm workspace; each package is built, tested, and published separately.
    This boundary is much clearer than Pinvou's:
    ```text
    Core does not know about the CLI
    Core does not know about the Anthropic SDK
    Core does not know about filesystem sessions
    Core does not know about MCP
    Core does not know about the product UI
    ```
    The runtime depends only on the core, and providers plug in as optional packages.
    ---
    ## The biggest highlight: the crash window is handled seriously
    Many agent frameworks' tool-call logic looks roughly like:
    ```ts
    const result = await tool.execute(args);
    history.push(result);
    ```
    The problem: if the process crashes after the tool executed but before the result was written to history, you cannot know whether the tool actually succeeded.
    For example:
    ```text
    The agent calls "transfer money to the customer"
    → the bank API has already succeeded
    → the process crashes
    → the agent restarts
    → no success result in the log
    → it executes again
    ```
    Kiso persists BEFORE the execution:
    ```text
    tool_execution_started
    ```
    After success it writes:
    ```text
    tool_execution_succeeded
    ```
    If a restart shows only started, with no success or failure result, it marks the execution as:
    ```text
    uncertain
    ```
    Then it asks a human to choose:
    ```text
    rerun
    or
    abandon
    ```
    So it neither pretends to know whether the tool succeeded nor retries on its own. The event protocol clearly distinguishes execution start, success, failure, human ruling, and the uncertain state.
    ---
    ## `kill -9` is not a marketing slogan
    The project really wrote an end-to-end test:
    1. start Kiso in a real PTY;
    2. the first file edit succeeds;
    3. a second shell command is mid-run;
    4. a real `SIGKILL` is delivered to the whole process group;
    5. verify the on-disk event stream is not corrupted;
    6. confirm that exactly one execution is uncertain;
    7. start a brand-new process and run `kiso resume`;
    8. inject a human rerun ruling;
    9. the original execution trajectory continues instead of replaying from scratch;
    10. the third file edit completes, and a Terminal event is written.
    This is more solid than most projects that call themselves "durable agents".
    It does not merely save the chat transcript; it verifies:
    > **After a running agent is hard-killed, a new process can continue along the original trajectory.**
    ---
    ## The session store is not a simple JSON write either
    Its session store does quite a bit of database-level work:
    * Append-only JSONL
    * fsync after every event write
    * a single-writer lock per session
    * detects and repairs an incompletely written tail line
    * checks that event seq numbers are contiguous
    * uses CAS to stop a stale session handle from writing
    * once a disk write fails, the in-memory session is marked poisoned and refuses to continue
    Every event is **persisted to disk before it yields upward**. That means by the time the UI sees an event, it is in principle already durable.
    `AgentSession` likewise states explicitly:
    ```text
    1. user input is persisted first
    2. the kernel executes
    3. every event is persisted first
    4. only then is it handed to the consumer
    ```
    Approval decisions, uncertain-execution rulings, and context summaries are all persisted state.
    ---
    ## Its API also resembles a framework
    Usage:
    ```ts
    const agent = createAgent({
      model: "claude-sonnet-5",
      tools,
      store,
      adapter,
    });
    const session = await agent.session({ id: "demo" });
    for await (const event of session.run("inspect this project")) {
      // consume events
    }
    ```
    The high-level runtime is only responsible for putting:
    ```text
    model
    tools
    Provider
    Session Store
    permission policy
    Hooks
    Extensions
    ```
    together.
    This is easier for an ordinary TypeScript developer to understand than LingTai's Soul, Molt, Avatar, and Karma stack.

    # The project's strongest points
    ## 1. The north star is very clear
    It emphasizes only one thing:
    > **Reliable Agent Execution**
    Not a desktop AI operating system, not a digital life.
    So every capability in the README traces back to the same thing:
    * the event stream exists for recovery;
    * approval exists for recovery;
    * tool receipts exist for recovery;
    * the terminal event exists to end honestly;
    * compaction must also be replayable;
    * extensions cannot break the log semantics.
    The product logic is closed.
    ## 2. Sensitive to failure semantics
    It does not compress every failure into `error: true`.
    For example, it clearly distinguishes:
    * input parameter errors
    * a prerequisite not met
    * transient errors
    * fatal errors
    * model refusal
    * content filtering
    * context limit exceeded
    * human abort
    * max rounds reached
    Many frameworks look great on the happy path; on any failure everything collapses into strings. Kiso's design focus is precisely the failure path.
    ## 3. Sensible extension boundaries
    MCP is implemented as a standalone extension rather than invading the kernel:
    > An MCP server is converted into tools; the kernel does not need to know that MCP exists.
    That is right.
    The most common mistake agent frameworks make is that every capability eventually lands in one giant `AgentSession` class. Kiso specifies that packages communicate through the event stream and hooks — no second central hub is allowed.
    ---
    # But I also see a few real risks
    ## 1. "Exactly-once tool execution" is slightly overstated
    Strictly speaking, Kiso cannot guarantee exactly-once for every external side effect.
    For example, the process crashes here:
    ```text
    the bank has completed the transfer
    but tool_execution_succeeded has not been persisted yet
    ```
    Kiso still cannot know whether the transfer succeeded, so it can only mark it uncertain and let a human choose rerun or abandon.
    So a more accurate statement is:
    > **Crash-consistent tool execution with durable receipts and explicit uncertainty resolution.**
    Or, in Chinese:
    > **Crash-consistent tool execution with durable execution receipts and explicit resolution of uncertain states.**
    It handles this very well, but it is not general exactly-once in the distributed-systems sense.
    True exactly-once still requires the tools themselves to support:
    * idempotency keys
    * transaction IDs
    * state queries
    * deduplication mechanisms
    I would suggest not making "exactly-once" the main public promise, or people who understand distributed systems will challenge it immediately.
    ---
    ## 2. The 2,000-line limit could turn from discipline into dogma
    Capping the core's size is good, but a hard rule:
    > any PR over 2,000 lines is closed outright
    can cause a few side effects:
    * logic written overly dense to save lines;
    * complexity pushed into massive type definitions;
    * semantics that belong in the core pushed into the runtime;
    * plenty of comments do not count toward the line limit, so cognitive complexity does not actually drop;
    * the number of packages keeps growing, and the system's overall complexity grows with it.
    In fact, Kiso's `events.ts` already carries a great deal of durable-protocol semantics — the core is small, but its protocol surface is not.
    A better discipline might be:
    > the core must stay explainable and product-logic-free, with a soft cap; exceeding it requires an ADR.
    Rather than treating 2,000 as an immutable law of physics.
    ---
    ## 3. "Small core" is not "small framework"
    The core may be only two thousand lines, but the complete system still includes:
    ```text
    Core
    Runtime
    Providers
    Node Tools
    TUI
    CLI
    Evals
    MCP
    Skills
    Subagents
    Config
    Trust
    Compaction
    ```
    So the outward-facing message should be:
    > **Small kernel, growable framework**
    rather than letting users believe the whole framework is only two thousand lines.
    The README is actually already clarifying this, but the "2,000-line core" up front is still very eye-catching.
    ---
    ## 4. The session lock has extra environment requirements
    To obtain `flock`, the current session store spawns a `python3` helper process to hold the file lock.
    That is a bit odd for a Node/TypeScript framework:
    ```text
    using the Kiso runtime
    → the machine must also have python3
    → depends on Python for the flock helper
    ```
    It brings:
    * Windows compatibility issues;
    * slim containers have no Python;
    * Node users do not understand why a Python subprocess was started;
    * extra state after the lock helper crashes;
    * packaging a single-file CLI becomes harder.
    This is probably the most visible engineering debt today.
    Longer term, better fits are:
    * a native Node file-lock library;
    * a tiny Rust/N-API sidecar;
    * or a per-platform lock implementation;
    * allowing a store lock adapter to be injected.
    ---
    ## 5. The durable event schema will become a long-term burden
    All of Kiso's advantages rest on the event log, and that is also its biggest future maintenance cost.
    Once users' disks already hold:
    ```text
    0.1.5 events
    0.1.20 events
    1.0 events
    ```
    Future versions must replay those historical events correctly forever.
    This means:
    * events cannot be casually removed;
    * fields cannot be casually changed;
    * projections must stay backward-compatible;
    * compaction algorithm changes cannot alter old log results;
    * provider behavior changes cannot break history;
    * extensions cannot write unrecoverable state either.
    The project already handles these in legacy `compacted`-event compatibility, optional fields, and version semantics — the author is aware of the risk.
    But carrying such a large durable event union at the 0.1 stage will make future evolution hard.
    ---
    ## 6. It is still very early
    The current release is `0.1.23`, and the API and event protocol are still evolving fast.
    So today it fits:
    * framework authors;
    * agent-infrastructure developers;
    * internal agents that need auditing and recovery;
    * people willing to participate in early design.
    It is not yet ready to promise:
    > that installing it instantly yields a mature, complete, cross-platform Claude Code replacement.
    ---
    # Evaluated alongside Pinvou and LingTai
    ### Product clarity
    ```text
    Kiso > LingTai > Pinvou
    ```
    Every Kiso feature revolves around reliable execution.
    LingTai revolves around long-lived agents, but with a lot of worldview and terminology.
    Pinvou has too many horizontal features, and its main line is the fuzziest.
    ### Architectural restraint
    ```text
    Kiso > LingTai > Pinvou
    ```
    Kiso clearly separates kernel, runtime, provider, tool, surface, and extension.
    LingTai's TUI/Portal/kernel boundaries are fine too, but the whole system is very large.
    Pinvou most resembles a desktop product that keeps adding features.
    ### Long-term autonomy
    ```text
    LingTai > Kiso > Pinvou
    ```
    LingTai specializes in long-term goals, knowledge, roles, and sub-agents.
    Kiso mainly guarantees a reliable execution trajectory; it does not directly provide a long-term persona or knowledge-growth system.
    ### As an open-source agent framework
    ```text
    Kiso > LingTai > Pinvou
    ```
    On this dimension, Kiso is the most suitable of the three.
    ---
    # My final judgment
    **It is the one I rate highest among the three.**
    It does not chase an "AI universal workbench" and does not build an overweighted digital-life narrative; instead it found a genuinely hard and universal problem in agent engineering:
    > **How to make an agent's execution recoverable, auditable, adjudicable, and continuable after a crash.**
    Its current value is not "more features than Claude Code" but:
    > **Providing a reliable TypeScript base on which Claude-Code-class products can be built.**
    I would position it as:
    > **Kiso is a durable TypeScript agent framework for building coding agents that can pause, crash, resume, and remain correct.**
    In Chinese:
    > **Kiso is a TypeScript agent framework oriented toward reliable execution — even when a coding agent pauses, crashes, or restarts, it continues from the correct state.**
    The core direction is sound, and it is clearly more restrained than Pinvou and more like infrastructure. What matters most now is not adding more features but holding three things:
    1. make "crash consistency" an undisputed industry benchmark;
    2. lower the comprehension bar for the README and the event protocol;
    3. solve basic engineering issues like the Python `flock` helper and the cross-platform runtime.
    **Pinvou is a collection of features, LingTai is an agent worldview, and Kiso is the agent-engineering kernel.**
