# kiso code — the coding agent that survives kill -9

> Date: 2026-08-04
> Status: complete — all six delivery areas (A-F) landed, acceptance gate green
> Authority: direction ruling 2026-08-04 (user): the kiso code spec. All design
> pressure goes onto the reliability kernel — the extension surface (pi's

> out of scope for this round.

## 1. Goal

Position: **kiso code = the coding agent that survives `kill -9`.** Interrupted
executions get human verdicts, approvals persist across processes, and every
event is auditable and replayable. The CLI is a coding agent: bare `kiso`
enters chat, tool calls get one-line summaries, the status line shows usage
from honest usage events, and the whole story is proven by a real kill -9
end-to-end gate.

## 2. Non-goals (violations counted as scope creep)

- No TUI framework / React / Ink / blessed — all UI is ANSI line output.
- No new tools — the tools-node six-piece (read/list/search/write/edit/shell)
  is everything.
- No extensions / MCP / subagents (later stage).
- No dollar-cost display — tokens only, no price table to maintain.
- No new npm runtime dependencies.
- The core 2,000-line cap is immutable — the microcompact work had to fit in
  the then-current headroom (253 lines at ruling time).

## 4. Delivery areas

### A. Coding agent 化

- `kiso` with no subcommand enters chat (equivalent to `kiso chat`); the
  first argument is the session id.
- System prompt rewritten as a coding-agent constant (~80 lines, no template
  engine): workspace discipline, concise answers, tool discipline — read
  before edit, read before edit always, shell caution.
- AGENTS.md > CLAUDE.md (first match in cwd) is read at startup and injected
  into the system prompt, truncated at 8KB with a note; absent → nothing.
- The system prompt is byte-stable for the session's lifetime (D-zone
  contract).

### B. TUI four-piece (all ANSI line-level)

1. Streaming text — already there, kept.
2. Tool-call summary lines: one line per completed call —
   `✓ edit src/foo.ts (+12 -3)` / `✓ read src/bar.ts (140 lines)` /
   `✗ shell npm test (exit 1)` — edit/write show ±line counts, read shows
   lines, shell shows exit code; `isError` renders ✗. Full output is not
   printed by default; `/last` prints the most recent call's full
   input/output straight from the event log (no separate state).
3. Approval/uncertainty in-line interaction — semantics unchanged from the
   five hardening rounds (Ctrl+C semantics preserved); style unified with the
   new summary lines.
4. Status line after every terminal —
   `[turn 3 · in 12.4k out 1.8k · cache 9.2k · ctx ~14%]` — data from usage
   events only (honest: `?` when `known:false`), ctx% = chars/4 vs the model
   window (default 200k, `KISO_CONTEXT_WINDOW` overrides), always marked `~`.
   No counting API.

### C. MicroCompact — zero-API context relief (core, projection layer)

- Truth stays on disk; the projection replaces OLD compactable tool outputs
  with the fixed placeholder `[old tool output cleared: <tool> <primary-arg>]`
  when deriving model-visible messages.
- Whitelist: read_file / list_dir / search_text / shell outputs. write/edit
  outputs are short — never cleared.
- `do-not-compact` tagged receipts/results are never cleared (the existing
  tag mechanism, consumed directly).
- Trigger: never per-turn progressive clearing. When the estimated tokens
  (chars/4) exceed the threshold (50% of the model window by default,
  configurable via `microcompact: { thresholdTokens }`), the loop appends ONE
  `microcompacted` boundary event recording `beforeSeq` (KEEP_RECENT_TURNS
  user turns stay intact). The projection derives the cleared view from the
  boundary — the decision is a persisted fact: same events → same projection,
  byte for byte, across crash/resume. This is the deliberate difference from
  Claude Code's approach.
- Fits in core: implementation + schema change landed inside the 253-line
  headroom (final: 1,804/2,000). The new event type passed the existing deep
  validator (`isKisoEvent`) — same trust boundary as the adapter gate.

### D. Prompt-cache byte discipline

Contract: the same event-stream prefix projects to a byte-identical message
prefix (`JSON.stringify`, element for element); new events only change the
projection at the tail; the sole exception is the `microcompacted` boundary —
an explicit persisted fact whose replay derives the same projection.

Three regression tests (`packages/core/tests/prompt-cache.test.ts`):
① same log projected twice is byte-identical; ② appending a turn leaves the
old prefix byte-identical; ③ after a microcompact boundary, a reloaded
(JSON round-trip) log projects byte-identically to memory.

Written into the projection's doc comment (core) and the README technical
highlights section.

### E. kill -9 e2e gate (the acceptance core; in `npm run check`)

`apps/cli/tests/kill9.test.ts` — a REAL kiso chat in a REAL PTY (faux
provider, scripted trajectory: edit f1 → slow shell `sleep 30 && touch
marker.txt` → edit f3), killed with a REAL SIGKILL at the moment the second
execution's `tool_execution_started` lands on disk:

1. the agent's whole process group is SIGKILLed — no graceful shutdown;
2. plus the slow command's own DETACHED process group, discovered via `ps` —
   the shell tool spawns detached (so its timeout can kill the whole tree),
   and a real kill -9 of the scenario stops the running command too (this
   was a real finding: without it the interrupted execution "completes" 30s
   later and writes the marker);
3. assertions: stream loads uncorrupted; exactly ONE uncertain execution
   (the shell); marker absent; f1.txt edited; no terminal;
4. a FRESH process runs `kiso resume k9` — the uncertain verdict question is
   presented; `rerun` is injected over the PTY (zero human typing);
5. assertions: the ORIGINAL trajectory continues — the third edit happens
   (f3.txt = NEW), the terminal lands and is durable, the marker never
   appears, exactly one `tool_execution_resolved` on disk.

The fresh-process resume exposed a real gap, fixed in the CLI: the faux
provider's script counter is per-process, so a resumed process restarted the
script at turn 0 (re-issuing the first scripted call). The CLI now skips the
turns a session has already consumed — the session log is the durable script
position (tool results + end_turn stops + unfinished tool calls that the
recovery completes without the provider). The faux provider itself stays
counter-based: a request-derived index cannot replace it (a resume
continuation and the next run's first call produce structurally identical
requests and must receive different turns — only the instance counter
distinguishes them; proven by the runtime suite, which would need script
rewrites otherwise).

The README's "kill -9 test" section is the scripted version of this gate —
every claim in it is what the test actually asserts.
