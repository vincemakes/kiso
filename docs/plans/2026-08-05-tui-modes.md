## 1. The mechanism (kernel untouched)

The runtime's E1 approval chain (loop.ts Phase D) composes
`extensions[].approvals` with `deny > ask > allow` over ALL policies and
records `permission_decided` with `decidedBy: <extension name>`. The
five tiers are five in-process extensions named `mode:<tier>`, joined at
the chain head:

- only the CURRENT tier speaks — the others return `allow` (no opinion);
  the current tier always answers (allow/ask/deny), so the chain always
  terminates at it and the human flow only ever sees the current tier's
  `ask`.
- the current tier is FIRST in the array: an all-allow chain records
  `decidedBy = approvalPolicies[0]`, so an auto-allow under the startup
  mode names that mode honestly. Verdicts are order-independent (any
  deny/ask anywhere wins), so a user extension's deny beats
  `mode:bypass` — the monotonicity e2e pins it.
- the old static `PERMISSION_POLICY` is deleted; its semantics live in
  the `default` tier.

## 2. Two rulings the tests forced

1. **Unknown tools are the extensions' business.** mode:default's
   unknown-tool branch originally denied (`no policy rule ... (default
   deny)`) — inherited from the old PERMISSION_POLICY, which was the
   LAST resort and therefore never preempted extensions. On the chain
   head the deny DID preempt: the v2b/v2c/v2d e2e suite failed because
   the asky extension's `ask`/`allow` for `asky_read` was cut off. The
   tier now returns `allow` (no opinion) for tools outside its known
   sets — extension allow/ask/deny decide them, exactly as before. The
   old unknown-deny backstop retired with PERMISSION_POLICY.
2. **Headless children run bypass.** The subagent extension spawns
   child kiso sessions whose role policies are allow/deny only ("a
   headless child must never see an ask"). mode:default's `ask` for
   write/edit/shell stalled them. Children now spawn with
   `KISO_MODE=bypass` — the neutral tier, under which the role policy
   dir remains the child's only gate (deny>ask>allow honors its
   denials; the mode's all-allow never overrides them).

## 3. The wiring (apps/cli/src)

- `mode.ts` — the five tiers (`modeExtensions` returns KisoExtension[]
  with `.approvals`; current-first ordering), `modeFromEnv`,
  `modeSystemPrompt` (plan directive, injected into the composed
  systemPrompt at startup — the session prompt is fixed at creation;
  runtime switches are guided by the deny reason).
- `index.ts` — `extensions: [...modeExtensions(), ...loadedExtensions]`
  (banner unchanged — modes are in-process, never file extensions);
  `/mode` dispatch (show/list/switch, notice cell in the body,
  immediate status-bar repaint); status bar indicator (non-default blue,
  `⚠` for plan/bypass); `--mode <name>` flag (any argv position) and
  `KISO_MODE` env, applied before the first makeAgent; `/help` lists
  `/mode`.
