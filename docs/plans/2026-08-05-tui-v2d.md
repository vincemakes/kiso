## 1. Architecture (hard)

- **The ONE writer**: `body.ts`'s render loop is the only code that
  writes the scroll region; every event handler mutates a cell —
  interleaving is impossible by construction (the round's acceptance
  core, pinned by the lint e2e).
- **The cell model** (ours, not pi's Component shape — ADR-0040):
  UserCell / ThinkingCell / ToolCell / TextCell / NoticeCell / raw /
  terminal.
- **Freeze semantics**: completed cells print once and are never touched;
  the ACTIVE TAIL (unfinished cells) renders at the region's bottom and
  redraws in place (CSI 2026, the v2c cursor math). An over-height tail
  overflows to freeze by completion order.
- **Frame scheduling**: ≥16ms coalescing + a 200ms heartbeat (spinners /
  elapsed).

## 2. ToolCell lifecycle (the leak cure)

One line: `→ name 摘要` (≤60 chars) → ⏸ badge at an approval pause →
running (blue spinner + Ns) → frozen `✓ name (摘要, 1.2s)` /
`✗ name (错误首行, 1.2s)`. The [result] no longer flows (the body holds
the full data for /last); parallel tools each own a cell.

## 3. Pipes / non-TTY

Bypass the renderer; the Body's passthrough reproduces the v2b/v2c bytes
EXACTLY — the byte diff vs the v2c-era baseline (rebuilt from commit
a1309d2 in a worktree for an honest comparison) is EMPTY. Two integration
bugs found and fixed on the way: the passthrough thinking fold (the
buffer + close) and the dropped terminal label `\ndone\n`.

## 4. Tests

- Body unit tests (8): the cell→line forms, the freeze-once semantics

- The interleave-lint e2e (tui-v2d): three parallel tools + an approval +

## 5. Findings during the round

- The parallel-tools scenario revealed that the asky extension's `decide`
  asks for EVERY tool (its policy ignores the tool) — the approval
  questions are sequential (list_dir, shell, asky_read), and each answer
  is consumed by the editor's question mode. The test feeds answer each
  in order.
- The strip-based lint flattened adjacent rows (the "session" line
  merging into the banner) — the lint now reconstructs the lines at the
  cursor-positioning boundaries, then strips per line. A genuine
  interleave still lands inside one segment and fails.

## 10. #13 (P1) 返工 — 正文渲染器无滚出机制，B 路线修复

**发现#13**：冻结 cell 用绝对定位写入滚动区底行，溢出后 DECSTBM 区域内滚动——真实终端（Terminal.app 系）上区域内滚的行**不进原生 scrollback**，旧内容被原地覆盖（用户实测 LF=2 / CSI-S=0 / ESC-D=0 / 旧内容可见覆盖），违反 v2d 核心条款"冻结打印进滚动区、原生滚动保留"。

**路线选择（B）**：弃 DECSTBM 的经典底栏路线。正文不设边距——冻结内容用真实 LF 打印（终端自然滚动，scrollback 天然保留）；屏幕满前从顶绝对定位填充（不滚），满后每行 `\x1b[H;1H\n`（真实 LF，整屏滚动，顶行进 scrollback）+ 写正文底行（尾巴之上）；每次落地后重画 dock。代价=重绘流量略增（dock 每帧重画），换确定性的 scrollback 正确性——不依赖终端的区域滚动脾气（规格 ⚠ 已警示）。

**实现中发现的两个连带缺陷**（探针复现并修复）：
1. runtime 不发 `text_end`（adapter 层事件）——text cell 永不闭合，freeze 被堵，后续 done cell 全堆在尾巴里被心跳反复重绘（洪泛探针复现"flood 01 ×38"）。修复：新 cell 开始时关闭打开的 text（与 closeOpenThinking 同模式）。
2. 尾巴在冻结前切片——过期尾巴把已冻结 cell 再画一遍（"flood 01 ×2"）。修复：先算最终 nextFrozen/尾巴几何，再冻结，再画正确尾巴。

**验收**：
- 常驻门禁 scrollback-flood：24 行窗口灌 3× 视口（25 轮 × 5 冻结行），LF ≥ 104（滚动机制字节证据），早期内容恰一次（冻结语义），无 DECSTBM。
- 三终端：tmux `capture-pane -S -60` 上翻——早期 `session s13` 在原生 scrollback ✓；Terminal.app 10× /status 内容完整滚过 ✓（iTerm2 同构，AppleScript 无法上翻，以 tmux 的 scrollback 为机器证据）。
- 既有 v2d 断言零回归：交错 lint / 冻结恰一次 / 管道逐字节（与 v2c 基线 diff 仍为空）。
- 全量 498 绿（71 文件）。

**发布**：修复随下一版发布（本轮不单独发版）。
